Terminal and editor defaults

  • terminal.integrated.defaultProfile.linux is tmux; the automation profile stays /bin/bash, so build and task commands never wait on tmux. Plain bash and Grok Build stay available as extra profiles.
  • The tmux profile gives each terminal of a folder its own pane. The base session name is unchanged: vscode-<folder>-<hash>. A new terminal walks into one of that folder's sessions only while no client is attached to it, oldest first - that is the closed-tab rejoin, so a tab you closed or reloaded leaves its session unattached and the next terminal finds it with its history intact, and ssh + tmux attach -t <session> lands there too. A terminal opened when every session of the folder already has a client takes the next numbered sibling instead: vscode-<folder>-<hash>-2, -3, ... Sessions persist unattached until the container restarts, so a reattached terminal still reaches the output a closed tab produced. tmux ls lists the names and tmux list-clients says who is looking at each. Every target the helper gives tmux carries the = exact-match prefix (a bare name is answered by any session starting with it, so a closed foo could be answered by a live foo-2 and re-create the mirror), and a reopen whose session vanished mid-attach raises a fresh session rather than exiting along with the tab. Two tmux behaviors shape that path: a session raised by a tab's own foreground new-session has its first pane closed when that client exits (superuser#575909), which is why the helper creates detached and attaches separately; and with the default exit-empty the server itself leaves when its last session does (tmux#2081), which is why a reopen probes the server before raising anything - a tab whose server is gone has ended normally, and re-raising there would boot a server for a terminal nobody is looking at (tmux has no server probe: has-session answers the same for a missing session and a missing server, which is why upstream declined to add check-server, tmux#2523). No upstream issue accounts for the session loss: destroy-unattached is off, so a detached session is meant to survive, and tmux gives a session no grace period after it loses its last client (tmux#5821 is an open request for one).
  • One pane per visible terminal is what that rule buys. Clients attached to one tmux session share that session's current window, so a design that always reattaches makes every extra browser tab a mirror of the same pane: another full xterm.js in the Chrome tab re-parsing the same stream (each with a scrollback buffer preallocated from terminal.integrated.scrollback), another per-client encode in the tmux server, and a re-wrap repaint for every client each time any client activates or resizes. Measured on this workspace: 14 attached clients against 2 real panes. Two terminals opening in the same instant can still land on one session - that same mirror, and rarer than a keystroke.
  • Grok Build keeps its own session, keyed off the repository: the helper walks up from the terminal's folder with git rev-parse --show-toplevel (or uses the terminal's $PWD outside a clone), names the session grok-build-<folder>-<hash> after that root, and runs grok --cwd <repo root> inside it. A terminal opened anywhere inside the clone rejoins the one session the repository shares, and starts Grok Build at the repository root. That profile is deliberately the old always-reattach shape: watching the same agent run from several tabs is the feature, and the mirrors pay what mirrors pay. What the seed gives them is focus-events on, so a TUI in the pane can idle its animations while its tab is blurred, and escape-time 10, which keeps typing responsive on each of them.
  • With no tmux (offline first boot) the helper execs a plain login shell, so the default terminal still opens.
  • display_apps.web_terminal stays off: it would open a shell on the agent's working dir (/home/coder). A custom command-type coder_app named Web Terminal (order = 6, after VS Code Web at order = 5, before GitHub reauth at order = 7 and Install GitHub App at order = 8) takes that slot, cds to the clone folder - an empty repo_url keeps it on /home/coder - and execs a login shell. Like the built-in, it reads no terminal.integrated.* settings.
  • Neither template installs code-server through the Registry. Each main.tf carries an inlined fork (coder_script.code_server + coder_app.code_server), because the upstream module hardcodes /icon/code.svg and has no icon input. workspace installs code-server only when it is missing from /home/coder/.local/share/code-server and starts it with --auth none --port 13337 --app-name "VS Code Web" --ignore-last-opened <folder>, passing no settings payload. devcontainer has no persistent prefix to reuse, so it installs fresh under /tmp/code-server on every start.
  • The editor opens on http://localhost:13337/?folder=<urlencoded>: the coder_app resource in coder/coder ~> 2.18 has no folder argument, so the folder rides in the URL and as a positional argument to the code-server binary with --ignore-last-opened. workspace uses /home/coder/workspace/<repo> (and /home/coder with no repository); devcontainer uses /workspaces/<repo> inside a built dev container and /srv/coder-devcontainers/<workspace-id>/<repo> on the plain container. On first start the inlined coder_script.code_server creates that folder and waits up to 60 s for .git (skipped when the folder is /home/coder) so the clone can land before code-server launches. coder_agent.dir stays unset: the agent would chdir there before startup.sh, and a missing clone folder would fail the agent. With the sample REPO_URL that folder is /home/coder/workspace/evo-t1-coder-stack.
  • The icon travels as a data:image/svg+xml;base64 data URL read from templates/common/vscode-alt.svg: Coder serves icons only from its bundled /icon/* set or a full https/data URL, and that icon is not bundled. workspace_apps.icon is varchar(256) on Coder v2.36, so the SVG is a compact ribbon whose data URL fits that column; a larger file fails templates push with pq: value too long for type character varying(256).

Copy and paste between a tmux pane and the machine you type on

Two buffers are involved: tmux's own buffer, and the clipboard of the computer you are typing on. Which one a copy reaches depends on what sits at the other end of the terminal. Each claim below was measured in a headless Chromium against the code-server this stack ships (4.143.1, VS Code base 1.143.1).

  • A real terminal app honours OSC 52. Over ssh from Ghostty, kitty, WezTerm or iTerm2, Prefix-[, v, y puts the selection on the laptop clipboard. set -g set-clipboard on and set -g allow-passthrough on in templates/common/tmux.conf keep that route open for tmux's copy-mode and for an app inside the pane (vim's + register).
  • VS Code Web drops OSC 52. Neither a copy-mode y nor a hand-written printf '\033]52;c;<base64>\a' from the shell produces any clipboard call in the page: the terminal swallows the escape. Upstream microsoft/vscode#318254. A tmux copy made in the browser stays in tmux's buffer, and tmux show-buffer is where it is: a copy-mode y with nothing selected filled the buffer with the line the cursor sat on, and the page's clipboard stayed untouched. Prefix-] puts that buffer back into the pane, bracketed.
  • No modifier hands a drag back to the browser while tmux holds the pointer. With set -g mouse on, drags with Alt, Option, Shift and Ctrl each still arrived in tmux (its buffer changed; xterm painted no selection), so the "hold a modifier to select like the terminal does" escape hatch the tmux FAQ describes for desktop terminals is absent here.
  • Prefix m is the switch, and the browser's own selection is the route. Releasing the mouse makes a drag a browser selection, and the settings seed's terminal.integrated.copyOnSelection puts it on the system clipboard with no chord (a released drag showed the selected text in navigator.clipboard). In a browser tab: Prefix m to release the pointer, drag over the text, Prefix m again to give the wheel back to tmux. Output that has scrolled away: Prefix-[, then k (or Ctrl-u/Ctrl-d) walks up the pane's history until the line is painted on the screen, which is what the browser can select; drag it, q to leave copy-mode, Prefix m for the wheel. The switch lands during copy-mode as well, so finding the line first and releasing the pointer after works too.
  • Into the pane, nothing needs a switch. Ctrl+Shift+V, a plain Ctrl+V or Cmd+V (the browser's own paste event), and right-click each delivered the system clipboard to the shell, with a three-line paste arriving whole and without a warning dialog. tmux 3.4 already wraps its own buffer in bracketed paste on Prefix-].
  • Two scroll-back stores, two different budgets. terminal.integrated.scrollback in the settings seed is the xterm.js buffer, which is what a plain bash profile scrolls through; tmux's history-limit is what Prefix-[ walks inside a pane. They read 2000 and 100000 lines here, and the two numbers differ on purpose because the two stores are billed differently. VS Code preallocates the xterm.js buffer from the setting's value - its own description warns that "as the value increases, so will the amount of memory", against a VS Code default of 1000 (terminalConfiguration.ts) - and xterm.js keeps 3 Uint32 words per column per line (BufferLine.ts), so that cost is paid per terminal in the tab, and again per view of a pane. tmux holds its history once per pane, in the server, and every client of that pane shares the one buffer. Hence the split: the deep store is tmux's and the browser keeps a short viewport. Inside a tmux pane the wheel is copy-mode anyway (set -g mouse on), so the 100000 lines live behind Prefix-[ and nothing pays for them in the tab. Measured on tmux 3.4 with one pane pushed to its limit, 100000 lines of 120-column output holds the tmux server at 381 MB RSS; the same 100000 lines of plain 80-column output costs 60 MB. tmux reads history-limit when a pane is created, so an existing pane keeps the number it was born with.

grok doctor findings in a workspace

grok doctor checks terminal, clipboard and microphone support without starting a session, and /doctor inside a session adds the checks that need a live one. Each item in the Findings list carries its own fix, and --json prints the same report for a script. What the report should read here:

  • tmux options. templates/common/tmux.conf seeds the four options Doctor's own fixes write, set -g set-clipboard on, set -g allow-passthrough on, set -g extended-keys on and the *:RGB terminal-features entry, plus the xterm*:extkeys entry Doctor leaves to the operator. Those last two decide what survives the multiplexer: tmux rewrites 24-bit color down to the palette an attached client advertises, which is what makes a theme look washed out in the browser, and extkeys is what makes Shift+Enter and Ctrl+. arrive distinct from Enter. A client picks up terminal-features when it attaches, so after a reseed run tmux source-file ~/.tmux.conf and then detach and reattach (a refresh-client keeps the client on its old features). Proof: tmux display -p '#{client_termfeatures}' lists RGB and extkeys. tests/bats/tmux-fidelity.bats boots a scratch server on the seed and reads all of it back.
  • terminal.limited-color during an agent turn. A tool command launched by a running Grok session inherits NO_COLOR=1, FORCE_COLOR=0, CLICOLOR=0 and CARGO_TERM_COLOR=never from that session, so a grok doctor run from inside an agent turn reads color as off. The grok process itself and the tmux server carry none of those variables, so run it from a plain terminal for the real capability: the line reads color truecolor and themes all.
  • voice.no-input-device. Expected in a workspace. The container has no capture device at all (/dev/snd and /proc/asound are absent) and no recorder on PATH. The probe only looks for a recorder binary, so installing alsa-utils moves the line to available while capture still has nowhere to read from, and features.voice_mode = false leaves the finding in place. Neither would be a fix, so the stack ships neither and the finding stands as an accurate report of a headless container. Dictation belongs on a laptop-side grok. To give a workspace dictation instead: run PulseAudio on the workstation with its TCP module enabled, export PULSE_SERVER=tcp=<workstation>:4713 into the workspace, and install pulseaudio-utils there for parec.
  • terminal.ssh-wrap is a recommendation about the computer you type ssh on, since the wrapper has to sit in front of that client: run grok doctor fix ssh-wrap there, or grok wrap ssh <host> per connection. It forwards copies to the local clipboard and restores terminal modes when the link drops. /settings -> Show contextual hints -> SSH wrap silences the tip.
  • unavailable tmux and runtime probes. tmux.version, tmux.client-features and the runtime.* lines come back unavailable whenever Doctor has no interactive client of its own, which covers a piped run and a run from an agent tool call. Read them by hand (tmux -V, tmux display -p '#{client_termfeatures}') or from /doctor in a live session.

The Grok Build CLI in the golden image

  • Baked in at /usr/local/bin/grok, with an agent link beside it, outside the /home/coder home volume, so a rebuilt volume cannot lose it.
  • Pinned as GROK_VERSION in images/dev/tool-versions.env (1.0.70 at the time of writing, mirrored as the Dockerfile ARG default). The image build unpacks that pinned .zst and runs grok --version in two PATH contexts as a build-time smoke check.
  • Each template's startup script probes command -v grok on every start and re-downloads from https://x.ai/cli/install.sh - bounded, with retries - only while grok is missing from PATH. That installer follows the stable pointer, not this pin. It deliberately does not fetch on every boot: the bake-in under /usr/local/bin is the upgrade path, so shipping a new CLI means bumping the pin, rebuilding the image (scripts/build-dev-image.sh) and re-pushing the templates.
  • A self-installed CLI under ~/.grok/bin stays first on the login-shell PATH, so it wins over the baked copy.
  • The upstream /learn bundle never lands here: the 1.0.70 binary contains zero occurrences of the string /learn, so the bundled skill set is downloaded at runtime through the CLI's proxy endpoints config (cli-chat-proxy.grok.com, gated by GROK_SKILLS_BASE_URL) and needs an x.ai sign-in. This stack has no x.ai credential: LiteLLM is the sole model transport, with env_key = "LITELLM_API_KEY" and base_url http://host.docker.internal:4000/v1, so ~/.grok/bundled/ is never created, ~/.grok/skills/ does not exist, and grok inspect --json lists only the stack-seeded user skills. /learn is absent whichever CLI version is on PATH.
  • The stack therefore seeds its own /learn, so it is a stack payload like the delegation skill, not something to install: templates/common/learn.SKILL.md is written at workspace boot to ~/.coder/skills/learn/SKILL.md and twin-copied to ~/.agents/skills/learn/SKILL.md, each only while that file is absent - delete or edit either one to take it over. A seeded SKILL.md shows up in grok inspect --json as userInvocable: true on both the 1.0.70 CLI and the 1.0.44 copy baked at /usr/local/bin/grok, so this needs no image rebuild, and it reaches the Grok Build terminal profile because that profile execs the same binary. A user-scope skill shadows a same-named bundled one: if a workspace ever does sign in to x.ai, deleting ~/.agents/skills/learn/SKILL.md and the ~/.coder copy hands the slash name back to the bundled skill.

The rendered ~/.grok config

Rendered per workspace from templates/workspace/grok-config.toml.tftpl (and templates/devcontainer/'s copy of the same payload), and re-rendered idempotently while the managed block is intact.

  • At top level the render sets disable_web_search = true, which parks Grok's native web_search tool: no transport this box ships serves that tool type, so the self-hosted searxng MCP server is the search lane. The search lane section below carries the measurement and how to flip the key back.
  • [models] default points at the grok_default_model alias - agent unless the template variable or the create form's Grok default model dropdown names another. [models] default_reasoning_effort = "xhigh". The Spark lane answers low / medium / xhigh; high is never advertised.
  • The seven aliases (agent, agent-low, agent-medium, agent-xhigh, coder, coder-fast, chat) are defined with base_url set to litellm_url and env_key = "LITELLM_API_KEY". The key is injected as an environment variable, so it never appears in a file. agent carries three [[model."agent".reasoning_efforts]] tables (xhigh is the default). The agent-low / agent-medium / agent-xhigh aliases set supports_reasoning_effort = false because LiteLLM bakes the level for callers that have no reasoning-effort field.
  • [models] also carries extra_headers with x-litellm-session-id: ws-<workspace-id> - the key LiteLLM uses to pin a workspace's traffic to one healthy Spark box. Under a shared profile the last-booted workspace's key wins for the whole fleet.
  • github_mcp (default true, so the block renders unless you park it with GITHUB_MCP=false and re-push) adds the github HTTP MCP server (https://api.githubcopilot.com/mcp/), whose Authorization header references ${GH_TOKEN} by name, so no token value is ever part of a template variable. The agent environment fills it from the Coder External Auth provider (id github by default); a workspace whose owner connected no GitHub account renders the block anyway and pays one failed handshake per session.
  • context7_mcp (default true, parked the same way with CONTEXT7_MCP=false) adds the cached context7 stdio MCP server. Grok launches /opt/npm-global/bin/mcp-cache-proxy with --config /home/coder/.grok/mcp-cache-proxy/config.json, and that proxy fronts the official /opt/npm-global/bin/context7-mcp; both are pre-installed in the golden image, so nothing is fetched with npx at launch. The proxy config names $CONTEXT7_API_KEY and nothing else: the key reaches the workspace environment from the sensitive template variable context7_api_key, filled by the push from CONTEXT7_API_KEY in the host .env - not from Coder External Auth, which is what fills GH_TOKEN above.
  • grok_config_extra appends whatever the create form's Grok config extras field holds, verbatim under its own comment header.
  • [permission] holds the guardrails the stack owns; the approval mode itself stays a per-user call ([ui] permission_mode). Bash(rm -rf *) blocks the destructive form, and the dotenv family is split by what a file actually holds: the live .env and the populated suffixed shapes (.env.local, .env.*.local, .env.production / .env.prod, .env.staging / .env.stage, .env.development / .env.dev, .env.test / .env.testing, .env.ci, .env.override) are denied for Read and Edit, while the secret-free templates a repo ships (.env.example, .env.sample, .env.template, .env.dist, .env.defaults, plus the .env.*.example / .env.*.sample spellings) are named in allow, so an agent maintains the env key list without a prompt in any mode. Neither list is the old blanket **/.env.*: deny outranks allow, so the blanket form blocked the templates along with the live files and left the key list -- the file that keeps a real .env honest -- to drift. .gitignore carries the matching half on the git side: the whole family is ignored except the names allow lists.
  • Stack ownership of the file rests on either marker spelling: the line-1 managed-by: evo-t1-coder-stack comment or the top-level __evoT1Stack = true key. Both twins emit both, because the comment alone does not last - grok mcp add persists its own settings by rewriting the file and deletes every comment line, so a comment-only marker handed the config to the user with no human in the loop, and the default lanes silently stopped arriving. A hand-edited config is left alone only while it carries one of them, so takeover means deleting both lines; delete the file and restart to hand it back. When the guard does re-render, the CLI-owned tables [cli], [ui] and [marketplace] are carried over rather than wiped, because the stack owns no approval mode - [ui] permission_mode / yolo stays a per-user call.

Grok Build state: one shared profile per user

Every workspace gets its own /home/coder volume, and ~/.grok is a second, nested mount inside it: a Docker volume named grok-profile-<owner-id>, referenced by name rather than declared as a Terraform resource, which every workspace of that owner mounts read-write at the same path while that workspace is in shared mode.

The two modes

  • shared (the default here, so a workspace gets the profile unless you turn the mode off): configure the CLI once and the rest of that account's workspaces inherit it.
  • private: that workspace's ~/.grok - config.toml included - lives on its own home volume, differs from its siblings, and dies with the workspace (or survives a rebuild on the same volume).
  • Set in two places: the template variable grok_profile_mode (GROK_PROFILE_MODE=shared|private in .env, forwarded by push-template.sh as --var grok_profile_mode), and the create form's per-workspace Grok profile field, which defaults to the variable. One workspace can therefore sit outside the shared profile while its siblings stay inside it.
  • Changing the mode needs a rebuild - the nested mount either exists or it does not. A workspace that goes from shared to private starts on an empty profile: nothing is copied, and the shared volume is left alone.

What is shared

In shared mode: config.toml, skills/, memory-v2/, sessions/, notes/ (the canonical copy of each repository's private scratch notes.md), and a CLI you installed yourself under ~/.grok/bin. The CLI's own skill directories, skills/ and bundled/, are never created here without an x.ai sign-in; the stack's skill seeds live under ~/.coder/skills and ~/.agents/skills, outside this volume.

notes/<host>/<owner>/<repo>/notes.md is keyed per git remote, so every clone a workspace holds — the primary and each additional repository — has its own file. What you edit is the regular file at the clone root: that is what the editor, the terminal and a nested dev container all see, since the inner container mounts the clone bind and has its own ~/.grok. The copy runs both ways, and not only at boot. Startup copies the live file here and restores it when a recreate leaves the clone with nothing or with only the seeded stub line, and then leaves one background watcher per container that repeats the back-copy about every 30 seconds (NOTES_SYNC_INTERVAL, in seconds) over every clone under $HOME/workspace; the devcontainer template watches its /srv/coder-devcontainers bind root instead, since those clones sit there rather than under the workspace home. The watcher is single-instance behind a non-blocking flock on $HOME/.notes-sync.lock, in the container's own home rather than the shared volume, because each of the owner's workspaces needs its own.

That is what makes "survives workspace recreate" true rather than a hope: an edit is on the volume within roughly one interval, so a recreate no longer waits on someone restarting the workspace to pick up what was typed since the last boot. What is not promised is the tail

  • a file written in the last two seconds is left for the next tick, because copying it whole could archive a half-saved file. Going the other way, two guards stop a recreate from erasing notes: a live file that is empty or still holds only the seeded stub never replaces a canonical copy carrying real notes, and a real canonical copy restores over such a stub in a clone. Before any substantive canonical copy is replaced it is archived as notes/<host>/<owner>/<repo>/backups/notes-YYYYmmdd-HHMMSS.md, keeping the newest NOTES_BACKUP_KEEP (10 by default), and that directory is where an operator recovers notes after an accident. grok_profile_mode=private mounts no shared volume, so those notes die with that workspace; shared is the default. Like config.toml, the last workspace started for a given user and repository wins.

Two things about that start are worth knowing before you go looking for a vanished setting. Boot writes git config --global core.excludesFile — but only when you have not set it yourself. Left unset it points at ~/.grok/notes/exclude, which lists notes.md and .scratch-notes.md, so from then on every git repository in that workspace ignores both names at any depth; if you already set the option, those two lines are appended to the file it names and nothing else about it is touched. Boot also drops the same two lines into each clone's own .git/info/exclude, which is the layer that works even with no global config at all. And when a repository tracks a notes.md of its own, the scratch file is written as .scratch-notes.md beside it instead — your clone is never asked to delete somebody else's committed file.

Caveats, honestly

  • Keyed by owner id, never host-wide and never cross-user: another user's workspace mounts a differently named volume, and a stop or start of a different user's workspace never sees the volume at all.
  • The memory and index files are SQLite, opened live by every workspace holding the mount, so two workspaces writing memory at once can race. Roughly in sync is the bar, not transactional sharing.
  • Two workspaces of one owner that both hold a clone of the same repository each run a notes watcher over the same canonical path, so there too the last write wins, tick by tick. The stub and empty guards and the backups/ archive are what bound the damage a losing tick can do; they do not merge two diverging files.
  • One shared profile is one config.toml for every workspace that owner owns, and the last boot to re-render it wins - for the default model, the affinity key and the config extras alike.

Search lane and MCP servers

  • searxng (SearXNG metasearch, host port 8181) is the search backend the stack runs for itself: keyless engines only, no key, no account, no request logging. A workspace reaches it through the host gateway, so the workspace networks stay untouched.

  • It is not a model transport, and the native tool is parked: both twins render disable_web_search = true at top level, so a session starts with no web_search tool at all. Measured 2026-10-25: no model transport this box ships serves that tool type. The agent group is LiteLLM in front of the Spark boxes (openai/Qwen3.8-Flash-Next), and it refuses the request before anything is fetched - tools of type 'web_search' are not supported: this server runs function tools only, HTTP 400. supports_backend_search = false does not route around it, because the client-side fallback still hands the model alias a web_search-typed tool, which is the exact shape that endpoint rejects. The fallback lane fails too: it is the coder alias, Ollama qwen2.5-coder:32b, and that model is not pulled on the host. So web_search = "agent" and supports_backend_search = false stay as they are - the role stays filled so re-enabling is a one-key flip - but while the key reads true nothing dials it.

  • The searxng MCP stdio server is what answers instead, and it is the search lane rather than a fallback: both templates render that block gated on search_mcp, which defaults to true. It dials $SEARXNG_URL (default http://host.docker.internal:8181), the same key main.tf puts in the agent environment. Measure the self-hosted lane with:

    An empty result page and "no answer" are different answers, which is why the probe reports which one it got. It also names every engine the instance has parked and the reason its backend gave (parked by its backend: google: access denied), read out of the reply body whether or not that reply found results - an instance running on half its engines is visible there before it starts answering empty. A park is temporary: SearXNG holds an engine out for search.suspended_times seconds after it refuses, so re-run before writing one off. --json adds engines_parked. It checks the service hop; grok mcp doctor searxng inside the workspace checks the MCP hop. The binary it launches (/opt/npm-global/bin/searxng-mcp-server) is baked into the golden image, so a probe that answers with results plus a failed handshake is a server, URL or port problem, not a missing package.

  • To put native search back on a transport that really serves the tool: flip the key to false in the seed - both templates/workspace/grok-config.toml.tftpl and templates/devcontainer/'s copy - and re-push, which applies it fleet-wide. For one workspace without a push, the create form's Grok config extras field appends free-form TOML verbatim to that workspace's file. Either way start a new session, and expect the same 400 back if the endpoint still answers function tools only.

  • MCP servers: the default render declares three - github, context7 and the gated searxng server, which is the search lane itself. Each is a boolean gate in the template, so one env flag parks exactly one block and a template re-push applies it fleet-wide: GITHUB_MCP=false, CONTEXT7_MCP=false, SEARCH_MCP=false. The searxng block names the pre-installed searxng-mcp-server binary (pinned in images/dev/tool-versions.env and baked into the golden image), is gated on search_mcp (default true) and dials the service above through SEARXNG_URL. That URL is one of six keys the render sets in [mcp_servers.searxng.env]; the others pin the bridge's own tuning rather than taking its compiled-in defaults: SEARXNG_TIMEOUT_MS (20s, above the instance's per-engine budget and equal to the probe's --timeout), SEARXNG_CACHE_TTL_MS (15 minutes, which switches on the bounded 128-entry response cache that ships disabled, so a repeated query stops re-dialling backends that already refused this instance), SEARXNG_MAX_RESULTS (a ceiling that keeps one search inside [mcp] max_output_bytes), SEARXNG_DEFAULT_SAFESEARCH (mirrors search.safe_search in searxng/settings.yml) and SEARXNG_DEFAULT_LANGUAGE (all, so an image bump cannot quietly start geo-filtering every agent search). The five offline stdio servers (filesystem, memory, sequential-thinking, git and time) stay pre-installed in the image (npm -g for the first three, uv tool for the Python two), but the rendered config.toml names none of them: the session traces collected on this machine called none of their tools, and a declared-but-unused server still costs every session its handshake time and tool schemas. Declare one by hand and check a stubborn server with grok mcp doctor <name> inside a workspace.

  • The github server (https://api.githubcopilot.com/mcp/) renders by default even though it needs a token and outbound network: with GitHub tools on, the agent can drive the repository it is working in, and the cheaper failure is the block that renders with no credential and pays one failed handshake per session. github_mcp (default true) is the gate; $GH_TOKEN comes from Coder External Auth, never from a PAT.

  • The context7 server (library and API docs) also renders by default, and is the only cached one. context7_mcp (default true) is its gate, and the block it renders runs mcp-cache-proxy in front of the official context7-mcp - two packages pinned in images/dev/tool-versions.env and baked into the golden image, so parking or restoring it is a flag plus a template push, while changing the packages themselves takes an image rebuild. The proxy keeps its SQLite cache under ~/.grok/mcp-cache-proxy/, which rides the owner's shared profile volume in shared mode, and the cache TTL is 12 h: the first lookup of a library reaches the Context7 API and needs both network and CONTEXT7_API_KEY (optional - empty means the public rate limit), while an identical lookup inside the TTL is answered locally. Two tools, in order - resolve-library-id, then query-docs on the id it returns. Prove it with grok mcp doctor context7 inside a workspace.

  • Prove all three at once with bazelisk run //scripts:mcp-check: it reads the rendered ~/.grok/config.toml, reports whether each lane is declared, whether its command= binary is present, whether the lane's credential and cache config are there, and what each server's handshake says. A binary the box cannot find is image drift (the running evo-t1-dev predates the npm bake), and the check prints the pinned npm i -g --prefix /opt/npm-global command that restores it.

  • What the agent is told about all this lives in ~/.grok/AGENTS.md, inlined from templates/common/GROK_BUILD_AGENTS.md. Two sections cover the lanes. Research lanes makes a lookup part of the normal loop rather than a last resort: context7 first for a library, framework, CLI or setup question (that two-tool order), the searxng tools for anything else on the web, web_fetch for a URL already in hand, and it states that native web_search is parked so nobody spends a turn rediscovering the 400. Tool output stays out of the parent context makes that tool use delegated work: the child returns a digest - numbered findings, each one claim, one source URL and at most two lines of support, no raw result dumps, confidence stated - and keeps the raw pages to itself.

  • Cline and Roo/Kilo are pre-wired to the LiteLLM proxy (endpoint from litellm_url, default http://host.docker.internal:4000/v1; model alias agent, with agent-low/agent-medium/agent-xhigh/coder/coder-fast/chat listed in __evoT1StackModels). The seed is settings.json.tftpl, copied onto the per-owner volume vscode-settings-<owner-id> (mounted at ~/.shared/vscode/settings.json) only while that file is absent, and symlinked from ~/.local/share/code-server/User/settings.json. Startup chowns that volume to the home owner before the first write (empty named volumes are root:root 755). Edits stick, and every workspace that owner has shares the file; delete it to copy the template in again. From the host it is the volume's settings.json:

  • A built dev container mounts neither the volume nor the symlink, so it is the one place the seed is merged instead of linked: the inlined coder_script.code_server fork bakes a base64 copy of it and writes it over the dev container's private User/settings.json (or merges over a copy that survived a rebuild, when jq is on PATH; without jq the existing file is kept). Edits inside a built dev container therefore survive neither a rebuild nor a look at the shared file. Everywhere else no settings map is passed at all, because a merge would replace the symlink.

  • Installing Cline, Roo, the Red Hat YAML extension and Material Icon Theme is a manual step in the Extensions panel (Open VSX by default). If an extension build names its settings differently, set the OpenAI-compatible endpoint and key in its UI.

Coder Agents (control-plane)

Coder v2.36.6 ships Coder Agents: a coding agent that lives in the Coder server - a chat UI and an API beside your workspaces, not inside one. A chat runs its tools (read_file, edit_files, execute, spawn_agent) against a workspace over that workspace's agent connection, and consults two pieces of per-workspace context first: an instructions file and any skills it discovers. The agent itself is upstream Coder, not a home-grown agent.

It is always on

The chat agent is compiled into coderd unconditionally.

  • CODER_EXPERIMENTS in .env (empty by default since 2026-10-08) has never gated anything about it: the old agents default was not a recognized experiment name, and the server logged ignoring unknown experiment and ignored it on every boot.
  • workspace_external_agent, the entitlement the docs name, gates external agents (Claude Code, Codex, ...), not this one, and nothing here needs it.
  • If you know a real experiment you want (chat-advisor, chat-virtual-desktop, ...), list it in .env and restart the coder service. Empty means no experiments on.

Model wiring

Scripted, idempotent, re-runnable, and already started from prod-stack / dev-stack up (--apply --wait, default 1800 s). Registering the first account is the only operator step: the seeder continues once an owner exists, and the Agents page is usable with no extra Coder UI setup. Print the plan:

--wait (or --wait=SECONDS) polls for that first owner instead of skip-0. The window is counted from the database's first "no owner" answer, so a slow buildinfo probe or a slow first query cannot spend it. SKIP_CODER_AGENTS=1 skips bootstrap and stack-up seeding. CODER_AGENTS_WAIT_SECS is what stack up forwards as --wait=.

A chat turn needs an enabled chat model config - the chat's own pick, else the deployment default, else it errors before the first tool call - and that wiring is what the script writes. It mints a short-lived admin API token from the stack's own Postgres (token_name 'stack-coder-agents', deleted by the trap, never printed) and drives the server's experimental chat API:

  • an openai-compat AI provider named litellm (not litellm-auto), base URL http://litellm:4000/v1 - LiteLLM over the compose network, server-side, authenticated with LITELLM_MASTER_KEY. The agent dials the in-process AI Gateway (aibridge), which forwards to the provider's base_url + /chat/completions, so /v1 has to be part of the base URL and the key has to match the live proxy: with .env leaving the key empty, compose still boots the proxy on its change-me-litellm interpolation default, and that default is what gets sent. Created when absent, drift-patched when an existing provider carries a drifted base_url or key.
  • chat model configs agent (context limit 262144, set as the default; LiteLLM bakes reasoning_effort xhigh), agent-low / agent-medium / agent-xhigh (same lane with a baked thinking level, not default), and chat (32768), for models not already registered. coder and coder-fast stay out on purpose: on this stack's IPEX-LLM runtime those weights return tool calls as plain text with no tool_calls, and an agent turn without callable tools cannot browse or edit, so registering them would only add a silently broken model to the pickers. context_limit is the agent's own compaction budget (a 70 per cent default compaction threshold applies), which is why it is pinned per alias.
  • pins for the four auxiliary lanes - general and explore (the two subagent types) take agent, compaction and title_generation (the helper calls) take chat - written only for lanes that carry no pin yet, so an admin's own pins stay in place.
  • a three-line system-prompt addendum, appended after Coder's default prompt text (include_default_system_prompt: true), that keeps the delegation and secret-hygiene rules which must hold even when a chat has no workspace attached.

Coder's optional AI Gateway proxy stays off - LiteLLM remains the model transport, which is why no AI-Gateway keys exist in docker-compose.yml.

The delegation sketch

Chat on the Agents page -> if the ask needs more tooling than chat has, Coder Agents provisions or uses a workspace through execute -> big multi-file tasks are delegated inside that workspace: a headless Grok Build CLI run, started backgrounded and polled:

Backgrounded and polled because execute waits only a short window per tool call (about a minute), so a synchronous foreground grok -p would die mid-run on any big task. Coder Agents then reviews the delegated diff, runs the project's tests, and commits. Subagents spawned by Coder Agents cannot create workspaces: provisioning decisions stop at the top-level chat.

What seeds the agent's context

Six files seed into every new workspace, on first boot and only while the file is absent:

  1. ~/.coder/AGENTS.md
  2. ~/.coder/skills/grok-build-delegation/SKILL.md
  3. ~/.agents/INSTRUCTIONS.md
  4. ~/.agents/skills/grok-build-delegation/SKILL.md
  5. ~/.coder/skills/learn/SKILL.md
  6. ~/.agents/skills/learn/SKILL.md
  • 1 and 2 are the Coder agent's default discovery paths.
  • 3 and 4 are the same text under the Grok Build CLI's convention, and the CLI is what execute-lane delegation drives. The chat agent dedupes skills by name, first match wins, home scope before a working-dir path, so one agent never loads a skill twice: the twins exist for the CLI, not as a second source for chat.
  • 5 and 6 are the /learn orientation skill, payload templates/common/learn.SKILL.md, on the same absent-only contract. Upstream ships that slash name only in a skills bundle behind an x.ai sign-in this stack does not have, so the seed is what makes /learn exist; deleting both copies is how you hand it back if a workspace ever does sign in. See the CLI section above.
  • The text of 1-4 is the orchestration protocol (fan-out / fan-in, the edit-conflict gate, probe-one-worker-first, verify-what-a-worker-actually-produced). It travels as templates/common/GROK_BUILD_AGENTS.md, staged beside the staged main.tf and read back with file() / filebase64(); templates/common/ keeps one copy for both templates, and the push stages it into each template's pushed copy.
  • devcontainer and workspace both seed it, so the seed is not fetched from GitHub any more: no web_search/web_fetch call is needed to inspect this repo, and the instruction text tells the agent so.
  • Both main.tf files deliberately set no CODER_AGENT_EXP_* env keys on coder_agent.main: those keys replace the agent's discovery defaults, and the defaults already cover exactly the seeded paths - the ~/.coder roots plus a working-dir-relative .agents/skills, which resolves inside the agent's working dir (/home/coder in workspace; in devcontainer with the toggle on, the cloned folder under /srv/coder-devcontainers/..., where a dev container built on the sidecar carries its own home and no seeded path is visible from inside it anyway).
  • Each seeded file carries the stack marker - the managed-by: evo-t1-coder-stack comment, or the "__evoT1Stack": true / __evoT1Stack = true key in a JSON or TOML file - in SKILL.md directly under the --- frontmatter, since the agent's skill parser requires frontmatter on line 1 and silently drops anything else. Delete a file to take it over; edit it and the stack leaves it alone. ~/.grok/config.toml is the one seed where deleting a file is not the way: it needs both marker lines gone, see The rendered ~/.grok config. Either way the marker never reaches the model: the agent strips HTML comments from injected instruction text.
  • The seeds live per workspace, on that workspace's own home volume. They are not on the shared ~/.grok profile volume above, and seeding does not care whether that mount exists.

What this is not

Coder Agents is control-plane-native. This stack does not wrap Grok Build: the wiring above teaches (skill + instructions) and equips (the workspace-side CLI with its LiteLLM alias) the native Coder agent to drive Grok Build when work is too big to hand-drive. Delegation is a taught habit, not the product.
