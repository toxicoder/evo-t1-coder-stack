What the two templates make

Two templates live under templates/, and a push covers both.

  • workspace (templates/workspace/) is the plain dev container.
  • devcontainer (templates/devcontainer/) is the DinD

    DinD

    Docker-in-Docker — a workspace's own sidecar daemon, addressed through DOCKER_HOST.

    -backed one.
  • workspace goes first, devcontainer last: a dependent template pushes last so a partial failure leaves the base template usable.
  • devcontainer reuses workspace's variables. repo_url exists in both; dind does not exist in devcontainer.
  • Each template dir keeps its own independent copy of the .tftpl payloads (startup.sh.tftpl, settings.json.tftpl, grok-config.toml.tftpl). Change one twin, change the other.

The templates/common/ payloads

templates/common/ exists once instead of twice, and both templates consume it. template_push_one stages every file in this list beside the staged main.tf; a missing one fails the push before the CLI runs.

Boot identity: rulebook, icon, notes, and terminal

  • GROK_BUILD_AGENTS.md is the orchestration-protocol seed text that becomes every workspace's ~/.grok/AGENTS.md (read with file(), chomped). It rides coder_script.agents_seed rather than the startup script, for the reason that section gives: it is the largest payload the twins inline.

  • vscode-alt.svg is the editor icon (read with filebase64()). It stays small enough that the resulting data:image/svg+xml;base64,... URL fits Coder

    Coder

    The control plane: provisions one Docker container per workspace over the host Docker socket.

     v2.36's workspace_apps.icon column (varchar(256)).

  • notes-setup.sh is the library behind each clone's private notes.md. The startup script inlines it with file() the same way, writes it into ~/.grok/, sources it, and calls notes_materialize per clone.

    • That call also seeds the ignore entries that keep the file uncommitted; see "What is shared" in docs/grok-build-and-agents.md for what it writes into git config.

    • Once every clone has been through it the same script calls run_notes_watch, which reaches notes_sync_start on the home owner's uid and leaves the container with one background watcher (NOTES_SYNC_INTERVAL seconds, 30 by default; one instance per container behind a flock on $HOME/.notes-sync.lock) copying each clone's notes back to the owner's notes volume between boots.

      • The workspace twin watches $HOME/workspace; the devcontainer twin passes its $dc_dir, because those clones sit on the /srv/coder-devcontainers bind.

  • tmux.conf is the fidelity config the startup script writes. grok-build-terminal.sh and vscode-terminal-tmux.sh are the two terminal launchers, and they ride coder_script "terminal_launchers" with the shared body templates/common/terminal-launchers.sh.tftpl rather than the startup argument, which is the one execve that runs out of room: nothing at boot runs either script, the code-server terminal profile is their only consumer. Helpers use $folder (not $${folder}) because file() contents are not re-interpolated.

The skill command seeds and the body that writes them

  • grok-build-delegation.SKILL.md and coder-agents.md are the Coder

  • ez-learn.SKILL.md, ez-skillify.SKILL.md and ez-create-skill.SKILL.md are the stack's three skill commands:

    • /ez-learn writes memory files, reproducing the upstream memory family /flush, /dream, /remember and /memory;

The rulebook body and the repository-conversion family

  • agents-seed.sh.tftpl is the coder_script "agents_seed" body that writes ~/.grok/AGENTS.md from GROK_BUILD_AGENTS.md. Marker-aware rather than absent-only: a copy still carrying the stack marker is rewritten on every start, and one whose marker lines a person deleted stays theirs. scripts/lib/config_seed.sh names the same file and target for the host-side reseed.

  • ez-bazel-first.SKILL.md, ez-strong-types.SKILL.md and ez-trunk-based-repo.SKILL.md are the stack's three repository-conversion commands, and they stand in for nothing upstream:

    • /ez-bazel-first puts every tracked file behind a target and budgets the glob()s

    • /ez-strong-types pins a strict checker profile per language and ratchets the broad-type census

    • /ez-trunk-based-repo turns environment branches into environments and unfinished work into flags.

    • The family's fourth member, ez-micro-plan.SKILL.md, converts nothing: it is the parent's dispatch protocol, the one that cuts a change into micro tasks a fleet of subagents can each finish alone.

    • It writes the dispatch plan to .grok/plans/<slug>/plan.md (Goal, Dispatch, Lanes, Tasks, Ledger, Not doing) with ctx/ briefs and results/ reports beside it, in the same shape the rulebook at ~/.grok/AGENTS.md tells the parent to expect, and the plan tree is git-ignored by templates/common/notes-setup.sh beside the two scratch note names.

    • Unlike the authoring trio these are not single files: three of the four shell out to a python helper, so ez-bazel-first carries ez-bazel-first.owned_files_check.py and ez-bazel-first.glob_budget.py, ez-strong-types carries ez-strong-types.type_baseline.py, and ez-micro-plan carries ez-micro-plan.plan_check.py, each written to a scripts/ subdirectory of the same skill directory.

    • The bodies name the ~/.agents spelling of those helpers, which is why the twin copy is not optional.

  • stack-repo-skills.sh.tftpl is the coder_script "stack_repo_skills" body that seeds that family, from eight chomp(file()) entries: one SKILL.md per command plus the four python helpers. It is a second body rather than eight more heredocs in the first one for the reason this whole file keeps repeating: each coder_script.script is its own execve argument with its own ceiling, and a family that ships helpers grows faster than one that ships a SKILL.md each.

  • trunk-refactor.SKILL.md is the /trunk-refactor command, the procedure form that converts a repository onto trunk-based development, and trunk-refactor-seed.sh.tftpl is its coder_script "trunk_refactor_command" body. It is the one command of that family with a body to itself: the four above already fill most of one argument, and adding a fifth SKILL.md to that map is what crossed the bound the first time.

Absent-only and silent on a healthy workspace, the way the two skill bodies above are.

Hooks, the MCP cache proxy, token refresh, and the vault fetch

  • hooks.evo-t1-hooks.json is the hook manifest Grok Build reads at ~/.grok/hooks/evo-t1-hooks.json, and five more files land under hooks/bin/ beside it: the four handlers it names (hooks.secret-guard.sh, hooks.dangerous-command-guard.sh, hooks.post-edit-format.sh, hooks.selective-test-runner.sh) plus the hooks.deny-patterns.txt the command guard reads one ERE per line. The manifest has to stay parseable JSON, so its stack marker is the "__evoT1Stack": true key rather than a comment line.

  • stack-hooks.sh.tftpl is the coder_script "stack_hooks" body that seeds that family, from six chomp(file()) entries, on its own body for the usual ceiling reason.

    Unlike the three skill bodies above it is marker-aware rather than absent-only: a copy still carrying the marker is rewritten on every start, because a guard that drifted from the seed silently changes what a session may run and what it may write.

    The four .sh files are written executable, with the payload's #! line kept on row 1, because the runner starts a relative command out of the manifest directly; the manifest and the deny list are data and carry no executable bit.

    What the four guards decide, and how an operator extends the deny list, is grok-build-and-agents.md.

  • mcp-cache-proxy.json is the context7 MCP cache-proxy blob the startup script writes, into ~/.grok/mcp-cache-proxy/config.json and only while that file is absent (that path is per workspace, so each workspace warms its own SQLite cache). How push-template works

bazelisk run //scripts:push-template runs scripts/push-template.sh.

  1. It resolves the repo root from BUILD_WORKSPACE_DIRECTORY (the real checkout bazelisk run names) ahead of the runfiles copy, so .env and the template files are regular files rather than execroot symlinks.
  2. It resolves the running stack on the Docker daemon by container label, never through a cwd-resolved compose project.
  3. Per template it checks main.tf exists (otherwise "run this from the repo root") and notes a missing .terraform.lock.hcl.
  4. It rejects a coder_workspace_preset description over Coder

    Coder

    The control plane: provisions one Docker container per workspace over the host Docker socket.

    's 128-byte ceiling.
  5. It rejects a vscode-alt.svg whose inlined data URL would exceed Coder

    Coder

    The control plane: provisions one Docker container per workspace over the host Docker socket.

    's 256-character workspace_apps.icon column.
  6. It streams the source as a tar on stdin, with symlinks dereferenced into regular files. Coder

    Coder

    's provisioner unpacks that archive into an empty workdir and does not follow host paths, so a stored runfiles symlink plans as "No configuration files".
  7. It confirms an active version.
  8. It re-sends the template's own description.
  9. It re-pins Autostop to Disabled.

The one-argument ceiling

The agent runs coder_agent.startup_script, and every coder_script.script, as bash -c <body>. The whole body therefore travels as one argument to execve(2), and Linux caps a single argument at MAX_ARG_STRLEN, 32 pages = 131072 bytes. Measured on this host: an argument of 131071 bytes execs and one of 131072 fails with E2BIG. Past the wall:

  • the agent logs fork/exec /bin/bash: argument list too long with exit_code=255 a few milliseconds in
  • the home directory never seeds
  • the workspace banner reads "A startup script has failed"

Which bytes make up the argument

The size that matters is not startup.sh.tftpl. main.tf composes the body from that template plus every templates/common/ payload it inlines, so any edit to the rulebook, the skills, the tmux config, the notes seeder, or the Grok config moves the number.

That is how six commits crept from 104 KB to 130 KB and one documentation commit crossed the wall at 135 KB.

Two things follow from the mechanism:

  • Each body is its own execve, so each gets its own ceiling. Splitting a body into two coder_script resources relocates the wall; it does not raise it. On this server (v2.36) the start scripts fan out concurrently in an errgroup and ready is set only after all of them return, so splitting does not reduce a peak either. coder_script_order needs Coder

    Coder

    The control plane: provisions one Docker container per workspace over the host Docker socket.

     >= v2.39.

    • This is the escape the stack now uses: the three skill payloads ride coder_script.stack_skills rather than the startup argument, because the devcontainer twin had 491 bytes of headroom left and three more inlined payloads could not fit there.

    • The same move later made room for the rulebook: GROK_BUILD_AGENTS.md is the largest payload the twins inline, and it left the startup argument for coder_script.agents_seed when that twin stood 196 bytes from the budget and one more instruction section could not land.

    • grok-build-delegation.SKILL.md still rides the startup argument - it predates the split, it fits, and its own tests pin it there.

  • A #! line does not help. The body still becomes execve(env, [env, bash, -c, body]); the interpreter line is content inside the argument.

How the push enforces the bound

startup_size_guard in scripts/push-template.sh enforces this before the CLI runs, beside the icon and preset-description guards. It sums each body's composed bytes and refuses the push past STARTUP_SIZE_BOUND (122880, which leaves 8 KiB, about two documentation-sized commits, under the kernel's own limit). Its reader is scripts/lib/startup_size.awk; //tests:bats_startup_script_size_test re-derives the same totals with an independent parser and pins the two together, so a guard that starts measuring something else goes red in review.

The guard also says the number while it is still a warning: a body within STARTUP_SIZE_WARN (4096) of the bound prints its composed total and the bytes left, because the distance to the budget is what a reviewer needs and a hard failure only ever reports the crossing.

Escape hatches when a body outgrows the bound

When a body really does need to grow past the budget, the options are:

  • Move the prose out. Rationale belongs in this file, not in startup.sh.tftpl. Comments in the template are bytes in everybody's argument; here they cost nothing.
  • Stage the payload as a file, not an argument. The obvious resource does not exist: the OSS provider's ResourcesMap (provider/provider.go) registers coder_agent, coder_agent_instance, coder_ai_task, coder_app, coder_metadata, coder_script, coder_env, coder_devcontainer and coder_external_agent, and nothing else. coder_file was requested in coder/coder#3055 and closed not_planned on 2022-09-23; a maintainer was still asking for it in 2025. Do not plan around it.
  • coder_env is the only provably-earlier file write. The agent's writeSecretFiles (agent.go) runs before any start script, MkdirAll 0700 then WriteFile 0600. It takes a string value, so it can carry a payload, and it writes into the agent's secret directory rather than anywhere you name.
  • CODER_SCRIPT_DATA_DIR is the per-script scratch the agent already hands you. agent/agentscripts/agentscripts.go appends CODER_SCRIPT_DATA_DIR and CODER_SCRIPT_BIN_DIR to every script's environment, which is a writable place to assemble something across scripts.
  • What is deliberately not done: bind-mounting templates/ into the workspace so the script can cat a payload off the host, and fetching one over HTTP at boot. The first couples boot to a host path that a template push rewrites, and the second puts a network dependency on the path that creates the home directory.

Argument handling

  • No arguments pushes every template in TEMPLATES_DEFAULT order.
  • Arguments are template names, and they select which names to push. A name that is not one of the known names is an error that lists the known names, so a typo cannot quietly do nothing.
  • A repeated name is one push, not two, and the push order stays TEMPLATES_DEFAULT order whatever the argument order is. Naming devcontainer first cannot orphan it.
  • It is also the manual path after you register an account, and the retry path for one template.

Credentials

The script mints a short-lived token by inserting a row into the stack's own Postgres.

  • Same trust model as coder reset-password, which also bypasses the API and talks to the database directly.

  • The token is scoped to minutes (CODER_PUSH_TOKEN_MINUTES, default 10), deleted on the way out including on a failed or interrupted run, never printed, and minted once for the whole run however many templates it covers.

  • Its scope has to be coder:all with allow_list {*:*}: a narrowed token fails the CLI's opening organization lookups, so least privilege is not available on v2.36.

  • Template source travels as a tar on stdin (coder templates push --directory -), so nothing is copied into the container or its volumes.

  • A push is also the only thing that registers a template: Coder

The three MCP switches and the search port

  • GITHUB_MCP, CONTEXT7_MCP and SEARCH_MCP share one polarity: all three MCP blocks ship from the template default (true), so the only value worth setting is false, and true/unset/empty pushes nothing at all.
  • The two research lanes split by question type: a library, framework, CLI or setup question goes to context7 (resolve the library id first, then query docs on that id), anything else on the web goes to the searxng search tool, and a URL already in hand goes to searxng's fetch_content. Grok's native web_search is parked here, and native web_fetch is unavailable because that tool needs an egress proxy endpoint this stack does not run, so SEARCH_MCP=false leaves a session with library docs and no way to reach the web.
  • A dev stack that moved the search port needs its own template push: searxng_url is derived from STACK_SEARCH_PORT as read from .env, so a push made while dev-stack.env carries 18181 still names 8181 unless the key is set in .env too. The vault keys and their two gates

  • The five values the boot reads the vault with are forwarded whether or not the flag is on (scripts/push-template.sh:696-730), so adopting the vault later is a re-push of one word rather than a re-config of five, and a stack that never adopted Infisical pushes none of them.

    None of the five is echoed either: a project id and a machine identity id both end up transcribed into whoever's CI log this output lands in, so the log line names only the key a value came from (scripts/push-template.sh:696-700).

    The sixth value, the instance URL, is the one a workspace cannot do without and the one this script composes rather than forwards, inside the flag gate (scripts/push-template.sh:652-661): .env's INFISICAL_URL is the address the host dials, and a container handed that spelling reaches its own loopback, where nothing listens.

  • The provider requires a parameter default to be one of its options, which is why a custom --var value is injected as its own option instead of being dropped.
  • A github_mcp of true with no GitHub account connected gives that workspace a server that fails its handshake once per session, because $GH_TOKEN is empty.

  • Park a lane deliberately with GITHUB_MCP=false / CONTEXT7_MCP=false in .env (relayed by push-template.sh) or --var github_mcp=false / --var context7_mcp=false on the push; a block missing from a render that got neither of those is a defect, not a park.

The container's clock is not a stage of this body: coder_script "tz_setup" settles it, from the shared body templates/common/tz-setup.sh.tftpl, because the startup argument is the one execve that runs out of room (see The one-argument ceiling). The TZ that env injects is resolved on the stack host, where the provisioner runs, from the three sources compose hands it:

docker-compose.yml carries TZ on the coder service as a null (TZ: ~) and bind-mounts the host's /etc/timezone and /etc/localtime into that container read-only, which is what the two reads above see. Without them the probe would answer the workspace image's own /etc/timezone, the baked default, and the feature would do nothing.

The null is the whole shape of the seam, because two readers share that one key and neither tolerates an empty value:

  • the server itself, which is Go, and Go reads a present-and-empty TZ as UTC and ignores /etc/localtime outright (time.initLocal: $TZ="" means use UTC);
  • the resolver above, which runs in that same container and asks env("TZ").

A null takes its value from the environment compose was handed, .env included, and drops the key entirely when nothing set it. Unset, and neither reader sees a TZ at all: Go loads the mounted /etc/localtime, coalesce falls through to the mounted /etc/timezone, and both answer the host. Set, and one IANA name answers both. An TZ: ${TZ:-} default, or an .env carrying a bare TZ=, is the failure mode that shape avoids - compose resolves either of them to a present-and-empty value and the server quietly runs on UTC while the host runs somewhere else. .env.example therefore ships the key commented out rather than empty, and tests/bats/workspace-tz.bats pins the null, the two binds, and this line.

A host that ships no /etc/timezone. That file is a Debian-derivative convention: a Fedora, Arch, or alpine-based host carries only /etc/localtime. Both binds use the long syntax with bind: {create_host_path: false} instead of the KEY:TARGET:ro short form precisely for those hosts, because the short form auto-creates a source the host does not have as a root-owned directory - at the container target, where file("/etc/timezone") then reads a directory and fails, and on the host, where it survives docker compose down and misleads the next dpkg-reconfigure tzdata. Why the stages sit where they do

The order above is not incidental; each line is a constraint the script has to keep.

The tmux seed and the clipboard route

  • ~/.tmux.conf is seeded before the two terminal helpers, which their own coder_script writes after this body returns. tmux reads that file once at server start and every terminal (plus an SSH client that reattaches) shares that one server, so seeding after the first tmux new-session -A could run would leave that session unconfigured for the whole boot.

    • mouse off is what keeps every click with the terminal client: tmux requests no mouse reporting, so a drag is the client's own highlight, the settings seed's copyOnSelection puts it on the machine clipboard, and right-click and middle-click paste it back.

    • Measured on the shipped tmux 3.4, an attach with mouse on writes ESC[?1000h, ESC[?1002h and ESC[?1006h to the client and an attach with it off writes none of them.

    • tmux keeps no clipboard of its own next to that: the copy-mode copies, the prefix paste ], the buffer picker = and the root-table middle-click paste are unbound, and Prefix m is only the switch that hands the wheel to tmux for a long scroll and hands it back.

    • set-clipboard on stays for the one copy route that is not tmux's own - an app inside a pane (vim's + register, anything that emits OSC 52) drives the machine clipboard through it, which is what a native terminal hands that app - and a client that blocks OSC 52 (iTerm2 by default) gets nothing at all, because there is no tmux buffer left to fall back to.

    • allow-passthrough ships off. What that option carries is the DCS-wrapped kind alone: a pane app's own sequences in tmux's ESC Ptmux; form, which the server hands to every attached client when it is on, and which is the class that turns into garbage on screen when a client downstream stops draining. The OSC 52 copy needs none of it (measured on the shipped tmux 3.4: that escape reaches a read-only client with passthrough off). Prefix p switches it for the one window that really wants its own sequences, and tmux show-options -gw allow-passthrough reads the value back.

    • The browser build of VS Code drops that escape as well (microsoft/vscode#318254), so a pane app's OSC 52 copy is silent in the tab and lands over ssh from a real terminal app, while the operator's own copy in the tab is the plain drag.

    • history-limit 100000 is priced, not guessed. Measured on the shipped tmux 3.4 with one saturated pane: 50000 lines of 120-column output holds the server at 193 MB, 100000 at 381 MB, and the same 100000 lines of plain 80-column output costs 60 MB. tmux applies the number to panes created from then on, so an existing pane keeps the limit it was born with (tmux(1)) and a new pane or a tmux kill-server is what takes a raise.

    • status-interval is the server's own periodic work: each tick re-expands the status line and runs the redraw pass for every attached client, the ones that stopped draining included. This tmux ships it at 15. Measured on the shipped tmux 3.4 with one attached client on a pane that writes nothing, over 16 seconds the stock status line took the same 1102 bytes at 1 and at 60, while the same client on a status line that changes every second took 6102 bytes at 1 against 1352 at 60. The stock status-right is %H:%M %d-%b-%y, so 3 of the stock 4 ticks a minute re-expand a string that cannot have changed; 60 is the finest step that string can show. The scope flag matters and only -g works: the same number written set -s status-interval is dropped at config load (measured -- the server keeps the stock 15 and reads nothing back), and a live server takes the value on tmux source-file ~/.tmux.conf.

    • set-titles off is a pin rather than a change: measured on a scratch server booted with -f /dev/null, off is what this build already defaults to, and the seed states it in the file the operator reads. One fewer string is pushed at every client each time a pane's title moves.

    • escape-time 10 is upstream's 3.5 default (CHANGES), chosen over the 0 that vim guides recommend. Measured on this build: Esc, 300 ms, q fires M-q at 500 and not at 10, while 0 splits an Esc from the character behind it whenever a throttled background tab delivers the two more than 10 ms apart. It is a server option, so tmux source-file ~/.tmux.conf moves it for live panes.

    • No option in the 3.4 set bounds a client that stops draining: client_output, client_buffer and client_last_activity all expand to nothing on this build, and the two pruning options are unusable here. Measured on a scratch server, destroy-unattached on (which accepts only off and on; dead comes back unknown value) destroys the session the moment its last client detaches, taking everything running in it, and exit-unattached drops the server the same way -- the opposite of what both launchers need, since a closed tab leaves its session unattached for the next tab to rejoin. The stale-client sweep in the two launcher payloads is what reaps a client like this; see grok-build-and-agents.md.

The hooks family, and why it is stricter

  • The guard family under ~/.grok/hooks/ follows the same rule for a sharper reason.

Stale editor swap files

The swap file's own persistence turns a killed editor into a permanent nuisance. Open vim ~/.grok/config.toml, stop the workspace with the editor still up, and the agent's process tree dies while the swap file stays on the home volume.

The next vim on that name stops with E325: ATTENTION and a question about a session whose container has been gone for days, and because "(E)dit anyway" leaves the swap in place and mints .swo, .swn, .swm beside it, an operator who keeps answering the prompt ends up with four of them and a prompt that never goes away.

Why the sweep lives in that body

The boot clears them, from grok_sweep_config_swaps in templates/common/agents-seed.sh.tftpl.

It runs there rather than in startup.sh.tftpl because the startup argument sits under a byte gate that holds the composed body to 110592 bytes (12288 of room under the 122880 budget this repo sets for itself, which is itself 8 KiB under the kernel's measured 131072 one-argument ceiling; see The one-argument ceiling), and the devcontainer twin already composes 110242 of those, leaving 350 bytes for everything else.

It also runs there because that body is already where a stack-owned file under ~/.grok is refreshed against its marker.

It does not lean on running after the startup_script: a coder_script runs in no promised order with it (templates/workspace/coder.tf:272), so the argument is the marker itself.

A config.toml that still carries the marker is one every start replaces from grok-config.toml.tftpl, whichever of the two runs first, so what an orphaned swap holds is doomed either way.

What makes the step safe

What makes the step safe is that it destroys nothing it cannot prove. Neither of its two checks establishes that a writer is gone. vim writes the swap once about four seconds after a change and then stays quiet while you read, so a live session idling over the file looks like a crashed one; and each workspace runs in its own PID namespace, so the /proc scan sees this container's descriptors only, which leaves a sibling workspace holding the same file open on the shared volume invisible from here.

So an orphan is moved into ~/.grok/stale-swaps/ under a name the sweep gives itself, and stays recoverable with vim -r for a month. The archived copy is re-dated to the moment it was set down: mv carries the swap's own mtime, and a workspace stopped for six weeks leaves a swap older than the retention, which that same boot would otherwise archive and prune in one breath.

A wrong call is one ls from undone.

  • It only runs when config.toml still carries a stack marker, either spelling of it, by the same contract as Marker ownership of the seeded files. A config that lost its marker is the operator's file, swap and all.

    The usual way one loses the marker is grok mcp add rewriting the file, and the remedy there is bazelisk run //scripts:seed-dev-env -- --force.

  • A swap written within the last hour stays. The hour is a courtesy toward a session that may still be open in a sibling container, which is exactly what the archive is for.

  • A swap some process in this container still holds open stays, read straight off /proc/*/fd and compared by exact path. Comparing it as a glob would let one bracket in $HOME hide a live holder.

  • Every path that cannot decide leaves the file where it is and says nothing:

    • a find or basename that is missing or errors
    • a readlink that cannot answer (the body runs it and checks the result instead of just looking for the binary, since an empty answer reads exactly as "no descriptor points here")
    • a /proc with nothing to scan
    • an archive directory that cannot be made
    • an archive name already taken
    • a mv that is refused

    The E325 prompt then waits for a person, which is a visible nuisance with no data behind it, while a wrong deletion is quiet and has data behind it.

  • Only vim's own .sw? suffix on that one name is a candidate, and a symlink at that name is left alone, since archiving a link would move the name and strand the bytes behind it. So .notes.md.swp and a .config.toml.newswp are never touched. Each move is announced on the body's log with the archived path in it, because the name carries a suffix nobody can guess.

  • The prune matches the sweep--prefixed names this function gives itself, at one level of ~/.grok/stale-swaps/ and no deeper, so a person who reads this page and parks a file in that directory keeps it.

The blind spot the design accepts

The blind spot the design accepts is a holder this process cannot see in /proc at all: a sibling container's vim, which the PID namespace hides, or a process whose /proc/<pid>/fd is unreadable from here. Its buffer and the archived bytes both survive, and the move is reversible for a month; what goes missing is the E325 prompt that would have warned the next person to open the file.

That window is narrow, it sits on a file every start overwrites anyway, and it is why the sweep stops at one name here.

  • The bound every body is written against: one agent's whole log stream - startup_script and every coder_script on it together - is 1 MiB.   • The repository URLs arrive as rendered literals and are read through a quoted heredoc, so no shell quoting has to survive and the value is only ever expanded as data. Cloning as the workspace user

  • clone_owner is whichever user the workspace really belongs to: the owner of $HOME when the agent runs as root, otherwise whoever is running the script. It decides both the chown target and whose git credentials the clone consults.

  • The parent folder (/home/coder/workspace, or the /srv/coder-devcontainers/<wsid> bind in devcontainer) is chowned before git runs, and non-recursively: other clones live alongside this one and are not ours to take over. The clone folder itself is chowned too, or a root agent leaves it root-owned and the clone dies writing .git inside it.

  • git never runs as root, so the credentials it consults - a helper, ~/.git-credentials, ssh keys - are the workspace user's.

    HOME is passed explicitly through env because runuser keeps the invoker's environment; a root agent would otherwise hand git /root and miss those files entirely. An empty prefix means "run git directly", which is correct for a non-root agent and for a root agent with no derivable workspace user.

  • A folder that already holds a .git is left alone: re-fetching is the user's call, because a pull there could conflict mid-edit or fail on a dirty tree, and either way the workspace would start on code nobody chose.

  • A failed clone is loud and non-fatal. The workspace still boots, an empty editor folder is fixable from a terminal, git removes its own partial clone on failure, and nothing in the script deletes a folder that may hold someone's work.

The credential ladder, in git's consult order

git never reads GH_TOKEN itself: it asks its credential helpers in order and sends the first answer. That order is what decides what github.com sees, and the first slot that answers wins outright - everything under it exists but a real push never reaches it, which is the whole difference between a credential that works and a push that works.

The five slots, in order

  1. The credential helper configured for https://github.com. Both template twins seed ~/.gitconfig at startup, for github.com and gist.github.com alike:

    The blank first value is git's reset marker: it drops any helper inherited from a lower-precedence config file, and git takes the last value it finds for that host.

    The startup seed rewrites both keys every start (idempotent), and github-auth fix installs the same form, leaving a helper that already ignores the pair alone. This helper is the slot that wins, and the clearing is the subject of the paragraph below.

  2. GIT_ASKPASS, when no helper answers. Where the staged binary is alive it mints on demand; where it answers unrecognized subcommand git gets no answer at all and falls through to prompting, which is where could not read Username comes from.

  3. The GH_TOKEN/GITHUB_TOKEN pair - reached through the helper, because gh auth git-credential echoes either name whenever one is set.

    A helper that does not clear the pair therefore answers with the injected copy and never asks the store: that is the shadow, and it is why a hand-edited helper or a hand-rolled askpass script is the wrong instrument (see the push-denied entry).

  4. The gh auth store (~/.config/gh, 0600): the one copy on disk, maintained by gh_token_refresh. Reachable only past a helper that clears the pair.

  5. A live coder external-auth access-token <id> mint, on demand. Not a helper: it is what github-auth fix calls, and what a workspace shell can call, whenever a token has to be certainly fresh.

After a reconnect, restart the workspace (or wait for the next gh_token_refresh) so the injected pair and the store match the new grant.

The refresh script unsets GH_TOKEN/GITHUB_TOKEN before gh auth login --with-token, because gh refuses stdin while those names are set.

A token that authenticates still has to be granted. A credential that was never GRANTED the repository fails clone and push, and reads prove nothing about write: a private repository hidden from the credential answers 403 or 404 on both lanes, and a public one answers a read probe with 200 for any authenticated caller, so a read-only credential passes a read test while every write to that repo is denied.

check therefore asks the write question directly: one GET of <repo>.git/info/refs?service=git-receive-pack, the endpoint git push itself negotiates through.

The four commands

Every one prints slot names, credential kinds and verdicts, and none of them prints a token. Repo convention: bazelisk run //scripts:github-auth -- <subcommand> ....
