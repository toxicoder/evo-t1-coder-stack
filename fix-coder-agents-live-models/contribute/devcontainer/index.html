Contributor environment

The one Linux golden image behind laptop work, the Coder workspaces and CI: what the contributor dev container builds, how it is seeded, and which path is the merge gate.

What's on this page

  • The single golden image, and the file that pins it
  • Opening the repo as a contributor container in VS Code or a compatible editor
  • What seed-dev-env materializes into that home, and what it refuses to touch
  • GitHub auth inside the container, and why github-auth check runs SELF there
  • The merge gate (Linux image) versus the convenience path (native Darwin)
  • What CI does, and why this repo's own Coder workspaces stay on workspace

What this enables

  • Reproducing CI's failure on your own machine with the same image CI runs
  • Running the Bazel gate on macOS without maintaining a second, BSD-flavoured toolchain
  • Telling the contributor container, the Coder workspace and the stack host apart in one look

One image — images/dev/Dockerfile, built as evo-t1-dev:latest — is the contributor and test runtime on macOS, on Linux, and on GitHub. The same Dockerfile serves the Coder workspaces the stack provisions, the contributor dev container on a laptop, and the container CI docker-runs its checks inside. Every version in it comes from images/dev/tool-versions.env; ../coder-templates.md covers the workspace side, and CONTRIBUTING.md is the checklist the PR follows.

The one image, the one pin file

  • images/dev/tool-versions.env is the single source of truth for every tool version: Bazelisk, buildifier, shfmt, shellcheck (apt), bats, Terraform/tflint/terragrunt, the Coder CLI, the Docker client trio, Node, Python, Go, protoc and the pinned Grok CLI.
  • Each KEY there is also an ARG in images/dev/Dockerfile, and the ARG default mirrors the pin, so a bare docker build matches a scripted one.
  • bazelisk run //scripts:build-dev-image refuses to build when a pin has no matching ARG, or when an ARG default drifted from the pin. Add both sides of a new pin in the same change.
  • The image ships the Docker client only. The build ends with test ! -x /usr/local/bin/dockerd (plus containerd, runc, docker-proxy), so the merge-gate container drives a daemon it is given rather than owning one.

Seeding the contributor home

scripts/seed-dev-env.sh materializes, into a laptop or CI home, the same stack-owned files a Coder workspace writes at startup — from the same template payloads, with no Terraform and no docker:

FlagEffect
--home <dir>Home tree to shape (default $HOME; created when absent; an existing non-directory is an error).
--litellm-url <url>Model-transport address rendered into settings.json and ~/.grok/config.toml (default http://host.docker.internal:4000/v1).
--context7-mcpKeep the [mcp_servers.context7] docs lane in the rendered ~/.grok/config.toml even with no CONTEXT7_API_KEY in the environment. Without it a keyless home renders the context7-free file, which is how a contributor ends up with a lane their workspaces have. The key stays optional: the server starts and answers at the public rate limit without one.
--devcontainerAfter a successful write, run gh auth setup-git when GH_TOKEN/GITHUB_TOKEN is set and gh is on PATH. Best effort, and the token is never an argument.
--forceRe-materialize files a user owns.
--dry-runPrint the plan; write nothing, create no directory, call no gh.

What it writes: ~/.tmux.conf, the shared ~/.shared/vscode/settings.json (with the code-server and desktop VS Code User settings symlinked to it), ~/.grok/AGENTS.md, ~/.coder/AGENTS.md, the rendered ~/.grok/config.toml, the two terminal helpers in ~/.grok/bin, ~/.grok/notes-setup.sh plus this clone's notes.md, and the ~/.grok/bin line in ~/.bashrc.

That notes.md is notes_materialize from the same library: it restores the canonical copy under ~/.grok/notes/<host>/<owner>/<repo>/ over a live file that is empty or still the seeded stub, and copies a real live file back there, so a stub never walks over written notes. Here that runs once, at seed time - the background watcher that repeats the back-copy about every 30 seconds is a workspace-startup thing (NOTES_SYNC_INTERVAL; see ../grok-build-and-agents.md) - so re-run the seeder to push a fresh edit to the canonical copy in this container.

Two rules decide every write, and they are the same rules the workspace startup applies:

  • A file carrying the stack marker - the managed-by: evo-t1-coder-stack comment, the "__evoT1Stack": true JSON key, or the __evoT1Stack = true TOML key - is stack-owned and is reseeded when the seed in this repo drifted. Taking ~/.grok/config.toml over means deleting both its marker lines, since the Grok CLI deletes comments when it rewrites that file: ../grok-build-and-agents.md.
  • A marker-free file is user-owned and stays untouched unless --force says otherwise. The terminal helpers and notes-setup.sh are the exception: startup rewrites those on every boot, so this script does too.

It never writes a secret, never writes a GitHub token or a PAT, and never installs the Grok CLI — the golden image already carries /usr/local/bin/grok. Exit 5 means no proven checkout was found (it wants docker-compose.yml where it is looking), which is the same repo-root probe every other script in the repo makes.

GitHub auth in the container

The contributor container is its own credential chain, so the doctor runs in SELF mode there — exactly as it does inside a Coder workspace:

  • SELF mode applies when CODER_WORKSPACE_ID is set or EVO_T1_DEVCONTAINER=1 is. The container sets the latter; a Coder workspace sets the former.
  • SELF means no docker at all and no DOCKER_HOST: one probe of this environment's own credential chain, printed as one self: line per credential. docker in here addresses the workstation daemon mounted in, never the stack host's workspace fleet.
  • Pass only the repository URL. A named container argument is refused with a pointer to the host shell, because that container lives on a daemon this environment cannot enumerate.
  • Credentials still arrive by the one supported path: Coder External Auth mints GH_TOKEN/GITHUB_TOKEN, and --devcontainer hands them to git through gh auth setup-git. There is no static token and no PAT in this repo's tooling.

Running the gate here

The merge gate is the Linux image, so run it in the contributor container:

From a machine that is not inside the container, ask the image to run them instead of installing the toolchain onto that machine:

That is the host ingress: it docker runs evo-t1-dev:latest as this process's uid:gid ($(id -u):$(id -g)), with HOME=/tmp and USER=$(id -un) so Bazel has a writable home and a name for a uid the image passwd file does not list, and runs the same suites CI runs. A macOS laptop gets the Linux result without a Linux box. Build the tag first with bazelisk run //scripts:build-dev-image if the daemon does not have it.

Native bazelisk test on macOS is a convenience, not a merge path. The suites run there, but the BSD userland differs from the GNU one the image ships (sed, date, find, sort), so a green Darwin run is not the run that gates the merge and a red one is not proof of a defect. The container, or test-in-image, is the answer test-with-bazel.md and ../branching.md gate on.

What CI does

.github/workflows/ci.yml builds images/dev with docker buildx build and the GitHub Actions layer cache (type=gha), then docker runs that image and runs the checks inside it: //:test-fast, //:lint, //:validate, and the docs-site/ Node checks.

  • No Actions container: key is involved. The job runs on a plain runner and reaches the toolchain through docker run --user "$(id -u):$(id -g)" with HOME=/tmp and USER=$(id -un), so what gates the merge is an image tag, the bind-mounted checkout stays writable, permission tests see a non-root identity, and Bazel can name a uid the image passwd file does not list.
  • The Bazel job no longer installs the pins onto the runner: the image already has them at the pinned versions.
  • A pull request that does not touch images/dev/** replays the cached layers instead of rebuilding them, which is what keeps the gate's wall time flat.

The equivalent run on your own machine is the host ingress above, so a CI-only failure is reproducible without a Linux box or a workflow rerun.

Why this repo's own workspaces stay on workspace

.devcontainer/contributor-env is a sentinel, not a config file. It is tracked in this repository, and probe_repo (in scripts/lib/workspace.sh) treats a clone that tracks it as a miss — exit 3 — even when the same clone also tracks .devcontainer/devcontainer.json.

  • The sentinel outranks every other signal, so new-workspace answers workspace for this repo and a Coder workspace of it never builds the contributor container on its DinD sidecar.
  • That container is the laptop and CI environment: it mounts the host docker socket and assumes a workstation daemon, neither of which belongs inside a workspace's nested dev container.
  • Do not copy the sentinel into another repository. An application repo's .devcontainer/ is exactly what new-workspace is supposed to find, and the sentinel in front of it silently downgrades that workspace to the plain template.

What this is not

  • Not the stack host. The compose host (gmktec) is bootstrapped with bash scripts/setup-host.sh, and it cannot be this container: it owns the daemon that runs Coder, LiteLLM, Ollama, Kasm, Homepage and Hermes. See ../project-conventions.md for the ingress rule that keeps that script the single documented bash scripts/….
  • Not a template change. templates/workspace/startup.sh.tftpl and templates/devcontainer/startup.sh.tftpl are untouched by any of this; the contributor seed reads them as payloads, it does not rewrite the twins.
  • Not a second toolchain. Nothing in the contributor path installs pins onto a laptop or a runner — that is what the image is for.
  • Not a credential store. GitHub auth stays Coder External Auth; no static token and no PAT appears in any file this page describes.

When the container itself is the suspect, bazelisk run //:validate from inside it is the fastest answer, and ../troubleshooting.md covers the stack-side failures it rules in or out.
