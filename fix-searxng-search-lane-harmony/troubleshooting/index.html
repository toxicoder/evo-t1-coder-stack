Troubleshooting

Symptom-first list of what breaks on this box: the error string, the cause, the recipe, and what the fix costs.

What's on this page

  • Stack bring-up: bootstrap, ports, containers that refuse to start
  • The model lane: Spark boxes, LiteLLM, and the agent backends
  • Workspaces: startup, the golden image, Grok Build (/learn, MCP), the toolchain
  • Docker-in-Docker, Terraform, and the host coder CLI
  • Editor, credentials, the clone, UI logins, and the public names (421, Chat 4403, Traefik)

What this enables

  • Starting from the error text you actually saw and landing on one command
  • Knowing the cost of a fix before running it, including what it destroys

Deep, symptom-first list. The operational dev-stack/prod-stack, search-check and spark-verify targets are described in README.md and project-conventions.md.

Each fence below is one copy-paste action. A heading quotes the error string where there is one, so start with grep -n on the text you saw.

Placeholders: <wsid> is a workspace id and <ws> a workspace name. The workspace container is coder-<owner>-<ws> (so coder-alx-self-coder); the <wsid> form names the DinD pieces around it - the sidecar coder-<wsid>-dind-sidecar, on the network coder-<wsid>-dind, with its own coder-<wsid>-dind-lib volume. What runs "from the stack host" needs a shell there: inside a workspace docker addresses that workspace's own private daemon through DOCKER_HOST=tcp://dind:2375, so a docker inspect aimed at the stack's coder or router container and run from inside a workspace queries the wrong daemon and answers no such container. bazelisk run //scripts:... also runs from the checkout.

Could not resolve host: github.com -> Tailscale MagicDNS is the only nameserver

Cause: /etc/resolv.conf names only Tailscale MagicDNS (100.100.100.100). Docker's iptables, and Kasm's privileged nested dockerd, can make that stub unreachable. When it is, every lookup dies, including github.com, so git pull over HTTPS fails. This is host DNS, not GitHub auth.

On Linux, bash scripts/setup-host.sh --repair writes /etc/systemd/resolved.conf.d/evo-t1-public-dns.conf (DNS=1.1.1.1 8.8.8.8), runs sudo tailscale set --accept-dns=false, and keeps MagicDNS for ts.net via resolvectl split-DNS. --check still writes nothing.

A checkout that does not yet contain that --repair (the usual case: git pull is already failing) needs the same commands by hand, then pull:

--check prints which nameservers are in play and whether github.com resolves. Other ways to keep a public resolver: add 1.1.1.1 / 8.8.8.8 as a global nameserver in the Tailscale admin DNS page.

The same MagicDNS-only resolver is what makes Terraform inside the coder container SERVFAIL registry.terraform.io (127.0.0.11:53: server misbehaving). That spelling lives under "Terraform and the host coder CLI" below. Compose pins public resolvers on coder so a template push does not wait on this host fix.

The TensorFold log is full of warnings, or resumed at 0 -> read the line shapes first

The server on each Spark box logs four shapes, and three of them are this stack's own traffic rather than anything wrong with the box. Read the shape before you reach for the box.

  • [tensorfold] done chatcmpl-... prompt=58 ... effort=xhigh tokens=16 finish=length followed by warning: a reply reached max_tokens while still thinking, so its content is empty: that is the LiteLLM proxy's health check, not a user. At the pinned tag the proxy sends the deployment's whole litellm_params through a real acompletion, so the lane's baked reasoning_effort rides along, and it asks for the default health_check_max_tokens of 16. A thinking reply cannot finish its reasoning in 16 tokens, so it returns empty content and the server warns about it. The reply is a healthy 200 and the deployment stays in the pool.

  • info: prompt cache: 80693 tokens, resumed at 79747, kept 1; 12 states, 6289 MiB and 0 MiB spare of 6465 MiB (hits ..., evicted ...): the box is out of prompt-cache room. resumed at N is how much of the prompt it did not have to recompute, so a healthy conversation logs a number just under tokens. resumed at 0 means it recomputed the whole prompt: something evicted that conversation's state. Watch evicted and the state count rather than any one line.

  • [tensorfold] ended chatcmpl-... reason=client-left prompt=... after=Ns: whoever asked hung up. A tiny prompt abandoned at around 81 s was a health check queued behind longer work; a huge prompt abandoned at around 400 s is a client with its own timeout, and it re-prefills from zero if it retries.

Two things on this stack cause the evictions, and both are tuned here rather than on the box:

  • Probe cadence. health_check_interval and health_check_concurrency in litellm/config.yaml decide how often every Spark deployment gets a real generation. They sit at LiteLLM's own default of 300 s and a concurrency of 2 on purpose: at 30 s across five deployments a round was putting more probes on a box than user requests, and each one took a prompt-cache state from a conversation. Auto-recovery does not need 30 s -- a box that is actually down is pulled by allowed_fails and cooldown_time under live traffic, and the re-probe is what brings it back. If the warnings come back every few seconds, that is the first key to look at.

  • The 195k needle. //scripts:spark-verify runs the recipe's needle.py --length 195000 as the window proof, and a 195k prompt the server has never seen is the largest single eviction on the box. It now skips itself while /health reports requests_running above zero, so it does not land on a box that is serving:

The window is still read passively on every run without the needle, from the server's own startup lines (context_pairs and startup_estimate in the report), so a box quietly rebuilt with a shorter window is still visible; the needle is the active confirmation of it. --no-tests skips all four recipe probes for a quick read-only pass, and that is what //scripts:bootstrap runs.

Workspace cannot reach LiteLLM -> CODER_ACCESS_URL, or host.docker.internal

Two lanes reach that port and they share nothing but the destination, so a probe on one answers nothing about the other.

  • The model lane: a process inside the workspace dials http://host.docker.internal:4000/v1 directly. host.docker.internal is the docker bridge gateway (172.17.0.1), compose publishes the proxy's container port 4000 on host port 4000, and nothing between the two authenticates. LITELLM_BASE_URL and the coding CLIs use this lane.
  • The app lane: the LiteLLM button in the Coder dashboard, at https://<coder name>/@<owner>/<ws>.<agent>/apps/litellm. coder_app.litellm sets subdomain = false, so that path rides the coder name and coder:3000, and litellm-gmktecbeast. is never consulted. See the next heading.

The checks that apply to either lane:

  • CODER_ACCESS_URL must be an https:// URL: a LAN IP, or the public coder name in public mode. Never localhost and never 127.0.0.1.
  • The workspace container must resolve host.docker.internal; the model lane reaches LiteLLM through that host gateway, and so does LITELLM_BASE_URL.
  • Agent traffic ignores that URL and dials host.docker.internal:3002; see the coder_agent_url template variable.

Search never answers (or answers empty) -> prove the search lane before blaming the MCP hop

The self-hosted SearXNG MCP stdio server is the search lane, declared by default (search_mcp defaults to true). Grok's native web_search is parked: the render sets disable_web_search = true, because no model transport this box ships serves that tool type - LiteLLM's agent group answers tools of type 'web_search' are not supported: this server runs function tools only (HTTP 400) before anything is fetched, and supports_backend_search = false does not route around it. An agent that still spends a turn on a native search call and comes back with that message behaved as configured; there is no native lane to fall back to. Two probes split a SearXNG fault in half:

  • bazelisk run //scripts:search-check (or scripts/search-check.sh from a shell that can reach the host gateway) dials the service directly. It reads $SEARXNG_URL before its http://127.0.0.1:8181 default, and every workspace's agent env carries that key, so a workspace-side probe needs no --url. It separates engines that answered, engines that were unresponsive, and an empty result page, and it names each engine the instance has parked together with the reason the backend gave (parked by its backend: google: access denied). A park expires after search.suspended_times in searxng/settings.yml, so re-run before writing an engine off. --json adds engines_parked for a dashboard to trend.
  • An agent whose searches come back empty while the service answers 200 is nearly always parked engines rather than a broken deployment: the general-purpose engines are the ones the public backends bot-wall first. The same query without an engines pin usually still returns results, which is why the guidance in ~/.grok/AGENTS.md tells an agent to leave the engine choice to the instance.
  • grok mcp doctor searxng inside the workspace probes the MCP hop. A healthy search-check plus a failed handshake points at the server, the URL or the port.
  • bazelisk run //scripts:mcp-check covers both hops plus the config side in one pass: the declared lanes, whether each command= binary is there, whether ~/.grok/config.toml is still stack-managed, whether the lane's credential is set, whether the search lane returns results for a plain lookup rather than just an HTTP 200, and each server's handshake. A missing binary prints the exact npm i -g --prefix /opt/npm-global command that puts it back.

There is no second lane behind this one, so run these probes before touching anything else. A service that answers but a server that will not handshake is the MCP hop; a server that cannot launch at all usually means no /opt/npm-global/bin/searxng-mcp-server, and that binary is baked into the golden image - an image that predates it needs a rebuild and a workspace recreate, not a config edit. Park the lane with search_mcp = false on the next template push (SEARCH_MCP=false in .env applies it to every new workspace) when a session should have no search tool at all. To restore the native tool, flip disable_web_search to false in both template twins and re-push - only for an endpoint that really serves the tool, or the 400 comes straight back.

Context7 or GitHub tools missing in Grok Build -> parked MCP block, or a handshake with nothing to authenticate

The three MCP servers (github, context7, searxng) ship by default. Park one with GITHUB_MCP=false / CONTEXT7_MCP=false / SEARCH_MCP=false in .env and a template re-push. bazelisk run //scripts:mcp-check reports the declared lanes, their binaries, their credentials and their handshake in one pass; grok mcp doctor inside the workspace lists the declared servers and their handshake.

  • A missing [mcp_servers.github] or [mcp_servers.context7] in ~/.grok/config.toml means the last push passed --var ...=false, or the workspace started from an older template, or the file carries no stack marker at all (next bullet). Re-push and restart the workspace so the managed config.toml re-renders.
  • A declared server whose command= the box cannot find is image drift: the templates declare a binary the running image never got, because it predates the npm bake in images/dev/Dockerfile. Rebuild evo-t1-dev and recreate the workspace, or install the pinned package into the running box (npm i -g --prefix /opt/npm-global searxng-mcp-server@<pin>, the pins live in images/dev/tool-versions.env).
  • A ~/.grok/config.toml carrying neither the managed-by: evo-t1-coder-stack line nor the __evoT1Stack = true key is a file the stack stopped managing, so neither the startup script nor the seed writes it again and its default lanes never arrive. The usual cause is not a hand edit: grok mcp add persists its own settings by rewriting that file and deletes every comment line, which used to revoke stack ownership by itself. The TOML key is what survives that write, so a config rendered by the current templates keeps its marker through grok mcp add. Take the file over deliberately by removing both lines. To give it back: delete the file and restart the workspace, or re-materialize it with bazelisk run //scripts:seed-dev-env -- --force.
  • A declared github server that fails handshake: the owner has not connected GitHub External Auth, so $GH_TOKEN is empty. Use the GitHub reauth app, then start a new Grok session.
  • A declared context7 server that fails handshake: empty CONTEXT7_API_KEY is the supported public-rate-limit shape. A key in .env plus a re-push fills the env; the block still renders with no key.
  • Discover live tool names with search_tool, then call use_tool with that schema. Do not hardcode MCP tool names from memory.

A workspace app link answers Bad Gateway -> find who answered

The LiteLLM and Open VS Code Web buttons are Coder apps: their URL is /@<owner>/<ws>.<agent>/apps/<slug> on the coder hostname, because both coder_app blocks set subdomain = false. So a failing app link is an app-lane failure, and a 200 from litellm-gmktecbeast. is not evidence about it.

Two hops can answer 502 on that path: this box's nginx, when coder:3000 will not resolve or connect, and Coder's own Go proxy, whose ReverseProxy ErrorHandler fires when the app upstream answers nothing. Two reads tell them apart, both from the stack host:

  • A hit in the first means Coder tried the upstream and gave up, so the fault sits on this box: check the devcontainer or workspace container first, then DOCKER_HOST.
  • X-Coder-Request-Id on the response, beside X-Coder-Build-Version, means Coder's own Go proxy answered, so Traefik and Cloudflare let the request through and the fault sits behind them. Nothing on this box sets Via or CF-RAY.
  • X-Evo-Proxy names the server_name that matched here: coder, litellm, kasm, homepage or hermes. Its absence means the request never reached this box's nginx.
  • Neither header, and a Server: cloudflare with a cf-ray instead: Traefik or Cloudflare answered, and there is nothing on this box to read.

To take the same reading from inside the workspace, replay the path on :8080, the published router port. That reaches coder:3000 through the sidecar while bypassing Traefik, Authelia and the WAN, so a reply there that differs from the browser's https:// URL names the cloud hops.

--noproxy '*' matters: with a proxy set in the environment curl hands the name to the proxy instead of resolving it, and 000 or a 5xx then describes the proxy.

  • 000 on the first probe means nothing listened on 4000. A 200 application/json means LiteLLM answered, so the model lane is healthy and the app lane failed somewhere else.
  • 000 on the second probe means the private lane is down as well, so the public failure is not a cloud-side one. 421 means the Host header matched no server_name here, which is what a rewritten Host looks like. STACK_ROUTER_CONF in .env names the conf those server_name lines live in; the vhost side of it is in UI and logins.
  • A 404 is what this stack answers for an unknown app slug or an agent that is not Connected; the agent is the text after the first . in <ws>.<agent>.
  • Signed into Authelia with the link still failing puts the fault behind Authelia: the app path is gated by the same policy as the rest of the coder name.

/learn missing from Grok Build on code-server web -> the CLI's skills bundle needs an x.ai sign-in this stack does not have

Cause: upstream /learn is a bundled user-invocable skill, but the bundle is not in the binary - the 1.0.70 executable contains no /learn string at all - so the CLI fetches it at runtime through its proxy endpoints config (cli-chat-proxy.grok.com, gated by GROK_SKILLS_BASE_URL), which needs an x.ai sign-in. LiteLLM is the sole model transport here, there is no x.ai credential, and the fetch never runs. The stack seeds its own learn skill instead, at workspace boot, into ~/.coder/skills/learn/SKILL.md with a twin copy at ~/.agents/skills/learn/SKILL.md, so a missing /learn means that seed is missing, not that the image is stale.

  • A learn entry with userInvocable: true in the grok inspect --json output is the pass condition: the slash command exists on that CLI, and the Grok Build terminal profile shows it because that profile execs the same binary.
  • No learn entry and both ls paths missing: the seed never landed, which means the workspace booted from templates pushed before the seed existed. Re-push the templates and restart the workspace, or reseed into the running container from the stack host: bazelisk run //scripts:refresh-configs -- --container coder-<owner>-<ws>.
  • Both ls paths present but no learn entry: the loader dropped the file. Frontmatter must start on line 1, so anything above the opening --- silently kills the skill.
  • A file you deleted or edited on purpose is not a fault: the boot reseeds each copy only while it is absent. Copy the payload back from templates/common/learn.SKILL.md to hand it to the stack again.
  • ls ~/.grok/bundled/skills printing nothing is the expected answer, not a symptom: without the sign-in there is no bundled cache at all, on any version. A user-scope skill shadows a same-named bundled one, so if this workspace ever does sign in to x.ai, deleting both seeded copies is what hands /learn back to the bundle.
  • ~/.grok/bin/grok first on PATH is a leftover installer copy: move it aside so /usr/local/bin/grok wins. That is the only PATH case, and it does not gate /learn.
  • The version line is still worth reading on its own terms: /usr/local/bin/grok in the current golden image is 1.0.44 while images/dev/tool-versions.env pins GROK_VERSION=1.0.70, so the image has not been rebuilt since the pin bump. Rebuilding images/dev (scripts/build-dev-image.sh) remains the CLI upgrade path - but the seeded /learn works on both CLIs, so do not rebuild the image to chase this symptom.
  • Pin notes and the seeding contract: grok-build-and-agents.md.

grok doctor flags voice.no-input-device or terminal.limited-color -> a headless container, and where you ran the command

Cause: both are properties of the environment. Neither points at a workspace that needs repair, and neither is fixable from inside the container.

  • voice.no-input-device: the container has no microphone and no recorder on PATH. The probe checks for a recorder binary, so installing alsa-utils makes Doctor answer available with nothing to record from; the image ships no recorder and the finding stays. The PulseAudio route that would make capture real: the voice bullet in grok-build-and-agents.md.
  • terminal.limited-color: a tool command spawned by a running Grok session inherits NO_COLOR=1. Rerun grok doctor from the terminal itself and the report reads color truecolor with themes all.
  • A tmux finding that survives a reseed of ~/.tmux.conf is a reload gap: a client reads terminal-features when it attaches. Run tmux source-file ~/.tmux.conf, detach, reattach, then tmux display -p '#{client_termfeatures}' and expect RGB and extkeys in the list.
  • terminal.ssh-wrap asks to be run on the workstation you type ssh on: grok doctor fix ssh-wrap there. Nothing a workspace installs satisfies it.

docker -> command not found inside a workspace -> an older image, or the wrong preset

  • Cause: that container was built from an image predating the Docker client toolchain, or from the bare-Ubuntu Minimal shell preset.
  • Rebuild the image, then rebuild the workspace; the image is fixed at create time.

Permission denied / jq: error: Could not open file on ~/.shared/vscode/settings.json -> empty named volume is root-owned

Docker-in-docker

Cannot connect to the Docker daemon at tcp://dind:2375 -> the sidecar, or DinD off

Cause: the sidecar is unhealthy, its image was never pulled, or the workspace was created with DinD off.

  • DOCKER_HOST is injected per template, not per toggle. templates/workspace sets it only while the toggle is on; templates/devcontainer sets it always, because that template always provisions the sidecar and the devcontainer CLI has to reach its daemon either way. So a set DOCKER_HOST tells you the template; the docker-in-docker metadata tile tells you the state (the devcontainer template always reads on (tcp://dind:2375), the workspace one reads off when unset).

Unexpanded count argument on block "coder_app.coder_ui" -> apps were gated on start_count

Cause: coder/preview warns when a coder_app count is not expanded at workspace-create preview. start_count is that value. The default is then assumed to be 1.

Fix: coder_app resources are not gated on start_count (scripts, metadata and the container still are). Push the templates; new creates stop showing the warning. Existing workspaces pick it up on the next update to the new template version.

bash: -c: line 32: syntax error near unexpected token '(' after "Running code-server in the background" -> HCL $$(( in the editor wait loop

Cause: Coder runs every coder_script as bash -c. HCL heredocs in main.tf only escape $${name} to ${name}; $$(( is two literal dollars. The editor wait loop then becomes waited=<pid>((waited + 1)), which is the syntax error. The echo before the loop still prints. already cloned, skipping on the next line is the concurrent clone stage, not the failure.

Fix: the increment is waited=$((waited + 1)) (one dollar). Push the templates and restart so the editor script relaunches.

Fix: the inlined fork starts code-server with --ignore-last-opened and the clone folder as a positional argument (/home/coder/workspace/<repo> on the workspace template). Push the templates and restart so the editor process relaunches.

A tmux copy in VS Code Web never reaches the laptop clipboard -> the browser build drops OSC 52

Cause: tmux pushes a copy out with OSC 52 and code-server's terminal hands that escape to nobody, so the copy stays in tmux's own buffer. Holding Alt, Option, Shift or Ctrl while dragging does not help either: with set -g mouse on the drag still reaches tmux.

  • Output already scrolled off the screen: Prefix-[, walk up with k until the line is painted, drag it, then q and Prefix m. The switch also lands while copy-mode is showing history, so releasing the pointer after you find the line works.
  • history-limit reads 100000 but a pane still forgets old output: tmux applies the option when the pane is created, so that pane keeps the limit it was born with. Open a new pane, or restart the server with tmux kill-server.

GitHub token expired, or the workspace has no GitHub account -> GitHub reauth

  • On the workspace page, click GitHub reauth. Coder opens /external-auth/<id> (device flow for the injected App, OAuth for a custom app in coder.env). If the page says you are already authenticated, click Reauthenticate.
  • If that page says "You must install the GitHub App to clone private repositories" and lists no accounts, the device-flow login already succeeded.   • Restart the workspace afterwards so GH_TOKEN and the gh auth store match the new grant. git via GIT_ASKPASS remints without that restart.
  • Existing workspaces pick up the buttons after bazelisk run //scripts:push-template and a workspace update to the new template version.

gh_token_refresh says gh would not store the minted token

  • The refresh script inherits GH_TOKEN/GITHUB_TOKEN from the agent. gh auth login --with-token refuses stdin while those names are set. Current templates unset the pair, log out, then log in with --git-protocol https, and print gh's stderr (token redacted) if that still fails.
  • Inside the workspace, run GH_TOKEN= GITHUB_TOKEN= gh auth status. Then click GitHub reauth, finish device-code login, install the Coder GitHub App if the reauth page says to, and restart.

Private-repo clone or push denied while a credential is present -> the grant, not the format

  • The denial is about the grant, not the credential format. A connected-but-unscoped credential authenticates and is still refused: 403, or 404 where GitHub hides a private repo's existence (a repo hidden from the credential answers 404, or 403, on the read lane and the write lane alike). And reads prove nothing about push: a public repo answers read probes for any authenticated caller, so a credential that READS a repo can still be refused every WRITE to it.
  • Check the GitHub side first. The grant behind the credential - the GitHub App installation that the External Auth provider (id github by default) minted its token from - has to include the repository the workspace clones or pushes. An empty github.com/settings/apps page is the usual surprise here: it means no App is installed under your account, so there is no Configure link to click and nothing to grant, while the provider itself stays configured and keeps minting tokens that authenticate. Install Coder's App from the workspace Install GitHub App button, or at github.com/apps/coder/installations/new, grant the repo, then restart. A private repository is never visible to a credential that was never granted it.
  • Then check the URL scheme. That credential covers https://github.com/... remotes only, so a git@github.com: or ssh:// URL gets neither helper nor askpass token and needs an SSH key you placed yourself, which this stack provisions nowhere.
  • The doctor, from a host shell or from inside a workspace, names the credentials a workspace's git and gh could present and answers "can this credential WRITE to the repo you pass?". It probes the endpoint git push negotiates through: one GET of <repo>.git/info/refs?service=git-receive-pack. A REFUSED-GRANT answer means the credential authenticates while every write to that repo is denied; NOT VISIBLE means the repo is hidden from the credential (or absent); REJECTED means github.com refuses the credential outright, as it does an expired mint:

On the host it enumerates the labeled workspace containers with docker and probes each (a named container checks just that one). Inside a workspace the docker CLI reaches only that workspace's DinD sidecar, so the same command runs SELF mode with no docker: one probe of this environment's own credential chain, printed as one self: line per credential. Pass only the repo URL there; a named container is refused and pointed at the host shell. The repo URL may be the clone URL or the browser URL, with or without a trailing slash and .git; a path below owner/repo is refused rather than probed, because it names no repository. Full usage: bazelisk run //scripts:github-auth -- --help.

  • --source=chain (the default) probes every credential that could answer for that repository; --source=env, --source=gh or --source=mint answers one slot and labels the answer shadowed when the env pair outranks it. That label matters: while GH_TOKEN/GITHUB_TOKEN carry a token, git and gh consult that token and never reach the gh auth store, so a PAT you pasted into the store is not the credential a push would use. To check or use the stored credential anyway, clear the pair for that one command:
  • Or install a write-capable PAT into one workspace's gh auth store, on stdin:

A manual PAT is legitimate in two cases: the workspace owner connected no Coder account, so nothing can be minted, or the minted/App credential is missing the repository - revoked or expired counts the same way, because the answer that proves either is NOT VISIBLE or REJECTED, not a passing read. It REPLACES the per-start minted credential for that workspace, so treat it as a stand-in and rotate or remove it in GitHub -> Applications when the work ends.

  • A PAT is never typed as an argument any more: argv is readable through ps and the token lands in shell history. Pipe it in (echo "$TOKEN" | bazelisk run //scripts:github-auth -- auth <container> -) or run auth <container> alone and answer the hidden prompt. In the line above, - is the only argument after the container and < PAT is a shell redirect, not an argument.

Public hermes-gmktecbeast answers 421 -> no vhost, a rewritten Host, or Traefik aimed past the router

Cause: this box's router answers 421 when the Host matches no server_name. The hermes vhost is not typed by hand: STACK_ROUTER_CONF in .env names the conf compose mounts (proxy/router.gen.conf, which bootstrap renders from proxy/router.conf.template, or the checked-in proxy/router.conf while that key is empty), and every server_name in it is composed from the naming parts. Under STACK_PUBLIC_HOSTS=auto a missing or mistyped part is what produces a name nothing answers. Traefik pointed at :9119 never hits that file. A rewritten Host also misses every block.

The public backend is the same hop as the other names. Replay it from a workspace, which reaches the published router and skips Cloudflare, Traefik and Authelia:

  • 421 means this box has no vhost for that Host. STACK_ROUTER_CONF in .env is what tells you which conf compose actually mounted, so read that file's server_name lines first, then recreate router so it picks up the one that lists server_name hermes-gmktecbeast.overeazy.io.
  • Anything else means the router matched (Hermes basic auth is 401 until you send credentials). A 421 only on the public URL, with this probe succeeding, is a rewritten Host or a Traefik backend that is not :8080.
  • Under auto both sides come from the same parts, so a 421 on a name nobody recognises is a part problem, not a router problem: an empty STACK_DOMAIN_BASE composes nothing (the stack stays LAN-only) and a mistyped STACK_SUBDOMAIN_SUFFIX or STACK_ENV_LABEL composes a name no vhost, no DNS and no certificate serves. Read the composed list back from STACK_PUBLIC_HOSTS in .env, fix the part, and re-run bazelisk run //scripts:bootstrap, then recreate. Editing the rendered proxy/router.gen.conf instead only survives until the next bootstrap, which re-renders it from the parts.
  • A part carrying an extra dot is the other failure this table cannot catch: the composed name sits more than one label under the zone, the wildcard does not cover it, and the browser aborts with ERR_SSL_VERSION_OR_CIPHER_MISMATCH before Traefik is ever reached, so no 421 is ever printed.
  • STACK_PUBLIC_HOSTS does not create the vhost. It is what bootstrap writes into STACK_HERMES_URL / HERMES_DASHBOARD_PUBLIC_URL for the Chat tab. bootstrap now also warns when a name in that list is missing from the conf it mounts.
  • The paste-ready Traefik file (one backend at :8080, passHostHeader: true, Authelia on the four interactive names, LiteLLM without Authelia) is in public-access.md#traefik-configuration.
