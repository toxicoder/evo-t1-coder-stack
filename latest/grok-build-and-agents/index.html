Terminal and editor defaults

  • terminal.integrated.defaultProfile.linux is tmux; the automation profile stays /bin/bash, so build and task commands never wait on tmux. Plain bash and Grok Build stay available as extra profiles.

  • The tmux profile gives each terminal of a folder its own pane. The base session name is unchanged: vscode-<folder>-<hash>. A new terminal walks into one of that folder's sessions only while no client is attached to it, oldest first - that is the closed-tab rejoin, so a tab you closed or reloaded leaves its session unattached and the next terminal finds it with its history intact, and ssh + tmux attach -t <session> lands there too. A terminal opened when every session of the folder already has a client takes the next numbered sibling instead: vscode-<folder>-<hash>-2, -3, ... Sessions persist unattached until the container restarts, so a reattached terminal still reaches the output a closed tab produced. tmux ls lists the names and tmux list-clients says who is looking at each. Every target the helper gives tmux carries the = exact-match prefix (a bare name is answered by any session starting with it, so a closed foo could be answered by a live foo-2 and re-create the mirror), and a reopen whose session vanished mid-attach raises a fresh session rather than exiting along with the tab. Two tmux behaviors shape that path: a session raised by a tab's own foreground new-session has its first pane closed when that client exits (superuser#575909), which is why the helper creates detached and attaches separately; and with the default exit-empty the server itself leaves when its last session does (tmux#2081), which is why a reopen probes the server before raising anything - a tab whose server is gone has ended normally, and re-raising there would boot a server for a terminal nobody is looking at (tmux has no server probe: has-session answers the same for a missing session and a missing server, which is why upstream declined to add check-server, tmux#2523). No upstream issue accounts for the session loss: destroy-unattached is off, so a detached session is meant to survive, and tmux gives a session no grace period after it loses its last client (tmux#5821 is an open request for one).

  • One pane per visible terminal is what that rule buys. Clients attached to one tmux session share that session's current window, so a design that always reattaches makes every extra browser tab a mirror of the same pane: another full xterm.js in the Chrome tab re-parsing the same stream (each holding a line-slot array sized from terminal.integrated.scrollback, with the cell data allocated per line as output arrives), and another full copy of the rendered stream through the pty. Measured on one flooding pane, 16 mirrors took 78.7 MB out of the server over an 8 s window where a single mirror took 4.9 MB, while the server's own CPU only moved from 420 ms to 630 ms - it renders the pane once, so a mirror is paid for in the tab. A client activating or resizing repaints the window's other clients too. Measured on this workspace: 14 attached clients against 2 real panes. Two terminals opening in the same instant can still land on one session - that same mirror, and rarer than a keystroke.

  • An attached client is not the same thing as a viewer. code-server's pty host keeps the pty open after the browser side of a tab goes away, so the tmux client stays attached, keeps its session's session_attached at 1, and receives nothing at all. Measured on this workspace's live server: 7 of its 9 clients received 0 bytes across a 4 s window of continuous pane output while the 2 tabs actually on screen each received all 12858 of them, and the quiet ones had reported no input for 30 minutes to 36 hours. That number is the whole reuse decision in the attach helper, so one of these is enough to make a free session look watched forever, and the folder pays a new session for every later tab. Both helpers now sweep their own sessions for a client that has been quiet past a 6 h grace before they read the snapshot; EVO_TMUX_STALE_AFTER (seconds) moves the number. Seeing the state yourself:

  • Grok Build keeps its own session, keyed off the repository: the helper walks up from the terminal's folder with git rev-parse --show-toplevel (or uses the terminal's $PWD outside a clone), names the session grok-build-<folder>-<hash> after that root, and runs grok --cwd <repo root> inside it. A terminal opened anywhere inside the clone rejoins the one session the repository shares, and starts Grok Build at the repository root. That profile is deliberately the old always-reattach shape: watching the same agent run from several tabs is the feature, and the mirrors pay what mirrors pay. What the seed gives them is focus-events on, so a TUI in the pane can idle its animations while its tab is blurred, and escape-time 10, which keeps typing responsive on each of them. Two things it does borrow from the attach helper: the session is created detached and attached in a second call, because the tab that brings the server up is otherwise the one that can take a running agent down with it (the same 9-of-20 loss the helper documents), and the stale viewers above are detached on the way in, which is where the 8-clients-on-one-pane count came from.

  • With no tmux (offline first boot) the helper execs a plain login shell, so the default terminal still opens.

  • display_apps.web_terminal stays off: it would open a shell on the agent's working dir (/home/coder). A custom command-type coder_app named Web Terminal (order = 6, after VS Code Web at order = 5, before GitHub reauth at order = 7 and Install GitHub App at order = 8) takes that slot, cds to the clone folder - an empty repo_url keeps it on /home/coder - and execs a login shell. Like the built-in, it reads no terminal.integrated.* settings.

  • Neither template installs code-server through the Registry. Copy and paste between a tmux pane and the machine you type on

One clipboard is in play: the one on the computer you are typing on. The seed runs set -g mouse off and unbinds every key and every click that could move text into or out of tmux's own buffer, so the terminal client keeps each button and does the copying itself, the way it does in a native terminal on that machine. OSC 52 is the one route that still depends on what sits at the other end of the terminal, and it belongs to an app inside the pane rather than to the operator. Where each claim below comes from: the tmux ones were read off the shipped tmux 3.4 on this box (what an attach writes to the client, and what list-keys still holds once the payload is sourced), and the setting names, values and defaults were read out of the shipped code-server 4.145.0's own config registry (VS Code base 1.145.0). The two Clipboard-API observations -- that a client selection fires navigator.clipboard.writeText, and that document.execCommand('copy') is the fallback that still lands on an insecure origin -- come from the earlier headless-Chromium pass over that build with the rendered settings.json twin and the tmux payload loaded, when mouse was still on and the copy out was a Shift+drag. That path is the client's own selection, which is what a plain drag drives now; the plain drag is due the same pass before it is restated as measured under mouse off.

  • Out of a pane: drag, and it is already on the clipboard. tmux asks the outer terminal for mouse reporting only while mouse is on: measured on tmux 3.4, an attach with mouse on writes ESC[?1000h, ESC[?1002h and ESC[?1006h to the client, and an attach with it off writes none of them. With the seed's mouse off tmux never sees a button, so a plain drag is the client's own highlight and the seed's terminal.integrated.copyOnSelection: true puts that highlight on the machine clipboard with no chord (the harness recorded navigator.clipboard.writeText firing on a client selection, before this switch).
  • Right-click and middle-click paste that clipboard. The seed sets terminal.integrated.rightClickBehavior: "copyPaste" - copy while there is a selection, paste when there is none - and pins terminal.integrated.middleClickBehavior: "paste", because the config registry in the shipped 4.145.0 gives that setting the default "default", which pastes only on the Linux build. tmux has no middle-click paste of its own to answer first: MouseDown2Pane is unbound in the root table.
  • tmux keeps no buffer, so there is nothing to paste out of one. Prefix-[ still enters vi copy-mode and it is a viewer: the cursor keys, PPage/NPage, Ctrl-u/Ctrl-d and k/j walk history, q leaves, and Escape clears a selection. Every copy that used to end a selection is unbound - Enter, C-j, D, A, the word and line copies a double- or triple-click fires, the copy a drag release ran, and the y the earlier seed bound itself - along with the prefix paste ] and the buffer picker =. Selecting inside copy-mode with Space, V or the cursor keys stays bound and is inert, with no copy command left for it to end on. Proof: sourcing the payload on a scratch server leaves list-keys with no copy command in copy-mode-vi, no paste-buffer or choose-buffer in prefix, and no MouseDown2Pane in root. The pointer's other jobs keep their prefix keys: Prefix-o or Prefix-q to select a pane, and Prefix-Alt-arrow to resize (plain Prefix-arrow selects a pane in the shipped 3.4's own default table).
  • Prefix m is the wheel, not a copy route. One press hands the pointer to tmux so the wheel walks pane history, the next hands it back. It is the escape hatch for a long scroll, because tmux paints in the alternate screen - it sends ESC[?1049h either way - so the client holds no scrollback of its own and a wheel over a pane has nothing to walk. Output that has scrolled away is copied by bringing it on screen first: Prefix-[, scroll it into view, select it with a client drag, q. A drag while Prefix m has the pointer on selects nothing, since the copy bindings stay unbound either way.
  • An app inside the pane drives the machine clipboard over OSC 52; the browser build drops it. set -g set-clipboard on with set -g allow-passthrough on stay in the seed for that one route: vim's + register, and anything else that emits the escape, reach the machine clipboard the way a native terminal hands them to it. Over ssh from Ghostty, kitty, WezTerm or iTerm2 that copy lands. code-server's browser build drops the escape before any clipboard call: a hand-written printf '\033]52;c;<base64>\a' was just as silent with set-clipboard off as with it on, which puts the drop in the browser and not in tmux. Upstream microsoft/vscode#318254 is open with two unmerged fixes, and the shipped 4.145.0 registers no OSC 52 setting at all, so there is nothing here to turn on. Nothing on the tmux side can spoil that clipboard either: tmux has no copy left to send, so an accidental selection in the pane cannot overwrite what the client just put there.
  • Into the pane: Ctrl+Shift+V or right-click, on a secure context. Both arrive bracketed (ESC[200~ ... ESC[201~) in a bash terminal and in a tmux pane alike, and a three-line paste arrives whole without a warning dialog. Both chords ask the browser's clipboard API, which the browser only exposes to a secure context, so the URL the tab was opened on decides it. On the TLS public name they work; on http://<LAN-address> navigator.clipboard is absent, right-click stops with VS Code's own toast ("This browser doesn't support the clipboard.readText API needed to trigger a paste, try Ctrl+V instead."), and the browser's native paste event is what still delivers. A Clipboard site permission that was once denied breaks both API chords the same way, with NotAllowedError: Read permission denied. Neither is a tmux route: the prefix paste ] and the buffer picker = are unbound, so the client's own clipboard is what arrives in the pane.
  • Ctrl+V on a secure origin is not a paste. VS Code binds terminal paste to Ctrl+Shift+V on Linux and Cmd+V on macOS, so Ctrl+V reaches the pane as the \x16 byte (readline's quoted-insert, vim's visual-block). The seed re-binds nothing there on purpose: a TUI in the pane owns that chord.
  • Two scroll-back stores, two different budgets. terminal.integrated.scrollback in the settings seed is the xterm.js buffer, which is what a plain bash profile scrolls through; tmux's history-limit is what Prefix-[ walks inside a pane. They read 2000 and 100000 lines here, and the two numbers differ on purpose because the two stores are billed differently. What VS Code preallocates from the setting is the buffer's array of line slots - xterm.js builds new Array(rows + scrollback) for it up front (CircularList.ts, Buffer.ts)
    • and the cell data lands one BufferLine at a time as output arrives, at 3 Uint32 words per column per line (BufferLine.ts), against a VS Code default of 1000 (terminalConfiguration.ts). So the setting costs a pointer array per terminal in the tab either way, and real memory only for the lines a pane actually emits - which is why a busy build log is where a large value is felt, and an idle prompt is not. tmux holds its history once per pane, in the server, and every client of that pane shares the one buffer. Hence the split: the deep store is tmux's and the browser keeps a short viewport. Inside a tmux pane the client's wheel has nothing to walk - tmux paints in the alternate screen, so that buffer holds no pane history - and the 100000 lines live behind Prefix-[, paid for in the server and not in the tab. Measured on tmux 3.4 with one pane pushed to its limit, 100000 lines of 120-column output holds the tmux server at 381 MB RSS; the same 100000 lines of plain 80-column output costs 60 MB. The same sweep repeated at 120 columns came out close to linear at about 3 KB of server per history line - 10 MB at 2000, 35 MB at 10000, 160 MB at 50000, 308 MB at 100000 - so this is the one terminal number that turns a chatty pane into real container memory, and it is a deliberate trade: the deep store is what lets Prefix-[ still reach the start of a build. tmux reads history-limit when a pane is created, so an existing pane keeps the number it was born with.

grok doctor findings in a workspace

grok doctor checks terminal, clipboard and microphone support without starting a session, and /doctor inside a session adds the checks that need a live one. Each item in the Findings list carries its own fix, and --json prints the same report for a script. What the report should read here:

  • tmux options. templates/common/tmux.conf seeds the four options Doctor's own fixes write, set -g set-clipboard on, set -g allow-passthrough on, set -g extended-keys on and the *:RGB terminal-features entry, plus the xterm*:extkeys entry Doctor leaves to the operator. Those last two decide what survives the multiplexer: tmux rewrites 24-bit color down to the palette an attached client advertises, which is what makes a theme look washed out in the browser, and extkeys is what makes Shift+Enter and Ctrl+. arrive distinct from Enter. A client picks up terminal-features when it attaches, so after a reseed run tmux source-file ~/.tmux.conf and then detach and reattach (a refresh-client keeps the client on its old features). Proof: tmux display -p '#{client_termfeatures}' lists RGB and extkeys. tests/bats/tmux-fidelity.bats boots a scratch server on the seed and reads all of it back.
  • terminal.limited-color during an agent turn. A tool command launched by a running Grok session inherits NO_COLOR=1, FORCE_COLOR=0, CLICOLOR=0 and CARGO_TERM_COLOR=never from that session, so a grok doctor run from inside an agent turn reads color as off. The grok process itself and the tmux server carry none of those variables, so run it from a plain terminal for the real capability: the line reads color truecolor and themes all.
  • voice.no-input-device. Expected in a workspace. The container has no capture device at all (/dev/snd and /proc/asound are absent) and no recorder on PATH. The probe only looks for a recorder binary, so installing alsa-utils moves the line to available while capture still has nowhere to read from, and features.voice_mode = false leaves the finding in place. Neither would be a fix, so the stack ships neither and the finding stands as an accurate report of a headless container. Dictation belongs on a laptop-side grok. To give a workspace dictation instead: run PulseAudio on the workstation with its TCP module enabled, export PULSE_SERVER=tcp=<workstation>:4713 into the workspace, and install pulseaudio-utils there for parec.
  • terminal.ssh-wrap is a recommendation about the computer you type ssh on, since the wrapper has to sit in front of that client: run grok doctor fix ssh-wrap there, or grok wrap ssh <host> per connection. It forwards copies to the local clipboard and restores terminal modes when the link drops. /settings -> Show contextual hints -> SSH wrap silences the tip.
  • unavailable tmux and runtime probes. tmux.version, tmux.client-features and the runtime.* lines come back unavailable whenever Doctor has no interactive client of its own, which covers a piped run and a run from an agent tool call. Read them by hand (tmux -V, tmux display -p '#{client_termfeatures}') or from /doctor in a live session.

The Grok Build CLI in the golden image

  • Baked in at /usr/local/bin/grok, with an agent link beside it, outside the /home/coder home volume, so a rebuilt volume cannot lose it.
  • Pinned as GROK_VERSION in images/dev/tool-versions.env (1.0.77 at the time of writing, mirrored as the Dockerfile ARG default). The image build unpacks that pinned .zst and runs grok --version in two PATH contexts as a build-time smoke check.
  • Each template's startup script probes command -v grok on every start and re-downloads from https://x.ai/cli/install.sh - bounded, with retries - only while grok is missing from PATH. That installer follows the stable pointer, not this pin. It deliberately does not fetch on every boot: the bake-in under /usr/local/bin is the upgrade path, so shipping a new CLI means bumping the pin, rebuilding the image (bazelisk run //scripts:build-dev-image) and re-pushing the templates.
  • A self-installed CLI under ~/.grok/bin stays first on the login-shell PATH, so it wins over the baked copy.

Three limits are worth knowing before you trust a clean scan, and each is a choice rather than an oversight.

  • The secret guard's generic assignment scan requires a digit on the matched line, which is what keeps a variable name from reading as a credential. The cost runs in both directions: api_key = XyZaBcDeFgHiJk (a name the list carries, no digit) walks through, and so does github_token_string = Abcd1234EFGH5678 (a digit, a name the list does not carry). What the fold does excuse is entropy sitting in the name position of a reference - os.environ/KEY_XyZaBc12345678 - because that position is where the correct pattern lives and the guard's whole job is to keep it writable. A missed shape is a line in hooks.secret-guard.sh, not a reason to trust the ones it does catch.
  • The command guard matches the whole command string, case-sensitively and byte-wise, so a command that quotes a denied form is refused the same way a real one is: awk '/dd if=/' notes.txt denies, and so does a commit message that names rm -rf followed by a space. The remedy for the rest is to rewrite the quoted sentence; the stack's own Bash(rm -rf *) permission deny behaves the same way for the same reason.
  • The deny list is a floor, not a fence. It catches the forms this repo has actually measured, and a novel destructive command walks straight through it. The rule the suite exists to enforce

Every multi-file change ends with an independent review panel that wrote none of it, on agent-review, before anything is reported done: three angles sent in one turn (requirements, proof, adversary), each owning no file, where one skeptic over all three angles is enough for a single-file fix. Grok Build state: shared state, per-workspace config

Every workspace gets its own /home/coder volume, and ~/.grok sits on it as an ordinary directory, config.toml included. What is shared is state: three nested mounts inside that home volume, one per concern, each a Docker volume named for the owner (grok-notes-<owner-id>, grok-memory-<owner-id>, grok-sessions-<owner-id>), referenced by name rather than declared as a Terraform resource, which every workspace of that owner mounts read-write at its own path while that workspace is in shared mode.

The two modes

  • shared (the default here): the three state directories ride their owner's volumes, so the notes, the memory and the sessions are the same files in every workspace that account owns, and they survive a rebuild. config.toml is not part of that share - each workspace renders its own.
  • private: no per-owner volume at all. The notes, the memory and the sessions live on that workspace's own home volume, differ from its siblings, and die with the workspace. config.toml is per workspace either way.
  • Set in two places: the template variable grok_profile_mode (GROK_PROFILE_MODE=shared|private in .env, forwarded by push-template.sh as --var grok_profile_mode), and the create form's per-workspace Grok profile field, which defaults to the variable. One workspace can therefore sit outside the shared state while its siblings stay inside it.
  • Changing the mode needs a rebuild - the three nested mounts either exist or they do not. A workspace that goes from shared to private starts on whatever those three directories already hold on its own home volume: nothing is copied, and the owner's volumes are left alone.

What is shared

In shared mode, three directories: notes/ (the canonical copy of each repository's private scratch notes.md), memory/, and sessions/ - one volume each, mounted at ~/.grok/notes, ~/.grok/memory and ~/.grok/sessions. Nothing else under ~/.grok is shared: config.toml, skills/, the MCP warm caches and a CLI you installed yourself under ~/.grok/bin are regular files on this workspace's own home volume, and those die with the workspace. The CLI's own skill directories, skills/ and bundled/, are never created here without an x.ai sign-in; the stack's skill seeds live under ~/.coder/skills and ~/.agents/skills, outside this tree.

The whole-profile volume this template used to mount over all of ~/.grok, grok-profile-<owner-id>, is still mounted in shared mode, but read-only and at ~/.grok-legacy, purely so the first start after that split can copy its notes/, memory/ and sessions/ across once: notes_hoist_legacy in templates/common/notes-setup.sh takes a concern only when the destination is missing or empty, and nothing reads that mount afterwards. A later chore: removes it.

notes/<host>/<owner>/<repo>/notes.md is keyed per git remote, so every clone a workspace holds — the primary and each additional repository — has its own file. What you edit is the regular file at the clone root: that is what the editor, the terminal and a nested dev container all see, since the inner container mounts the clone bind and has its own ~/.grok. The copy runs both ways, and not only at boot. Startup copies the live file here and restores it when a recreate leaves the clone with nothing or with only the seeded stub line, and then leaves one background watcher per container that repeats the back-copy about every 30 seconds (NOTES_SYNC_INTERVAL, in seconds) over every clone under $HOME/workspace; the devcontainer template watches its /srv/coder-devcontainers bind root instead, since those clones sit there rather than under the workspace home. The watcher is single-instance behind a non-blocking flock on $HOME/.notes-sync.lock, in the container's own home rather than the shared volume, because each of the owner's workspaces needs its own.

That is what makes "survives workspace recreate" true rather than a hope: an edit is on the volume within roughly one interval, so a recreate no longer waits on someone restarting the workspace to pick up what was typed since the last boot. What is not promised is the tail

  • a file written in the last two seconds is left for the next tick, because copying it whole could archive a half-saved file. Going the other way, two guards stop a recreate from erasing notes: a live file that is empty or still holds only the seeded stub never replaces a canonical copy carrying real notes, and a real canonical copy restores over such a stub in a clone. Before any substantive canonical copy is replaced it is archived as notes/<host>/<owner>/<repo>/backups/notes-YYYYmmdd-HHMMSS.md, keeping the newest NOTES_BACKUP_KEEP (10 by default), and that directory is where an operator recovers notes after an accident. grok_profile_mode=private mounts no shared volume, so those notes die with that workspace; shared is the default. Like the memory tree, the last workspace started for a given user and repository wins.

Two things about that start are worth knowing before you go looking for a vanished setting. Boot writes git config --global core.excludesFile — but only when you have not set it yourself. Left unset it points at ~/.grok/notes/exclude, which lists notes.md and .scratch-notes.md, so from then on every git repository in that workspace ignores both names at any depth; if you already set the option, those two lines are appended to the file it names and nothing else about it is touched. Boot also drops the same two lines into each clone's own .git/info/exclude, which is the layer that works even with no global config at all. And when a repository tracks a notes.md of its own, the scratch file is written as .scratch-notes.md beside it instead — your clone is never asked to delete somebody else's committed file.

The three stack-seeded skill commands

One line each: /ez-learn turns a session into durable memory - flush it into a session log, dream the logs into organized memory, remember one note, or browse and clear the store; /ez-skillify captures the session that just worked, working from its own transcript; /ez-create-skill builds a skill from what the operator describes. The last two write skill files; /ez-learn writes memory files.

Three things about skills matter in practice here:

  • Write a specific description and when-to-use. That text is what the model matches on, so a vague one leaves the skill reachable only by its slash name.
  • Set disable-model-invocation: true when only an explicit /name should run it. Anything that deploys, pushes or resets belongs behind that key.
  • After creating or editing anything, check discovery and provenance with grok inspect, and grok inspect --json for each skill's source path and userInvocable. /skills opens the same set as a menu, where a toggle takes a skill out of the slash menu without deleting the file. Discovery reloads from disk, so an edit lands next turn with no restart.

This is workflow curation, separate from the memory system, which stores durable facts (upstream /remember, /memory, /dream, shipped here as /ez-learn), and from AGENTS.md, which is the always-loaded rules file. A skill loads when its description matches, and holds a procedure.
