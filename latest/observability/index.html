Observability bundle

The ten profile-gated monitoring services: what each one does, how metrics, logs and traces reach Grafana, how an alert reaches Alertmanager, where each config file lives, what the data costs on disk, and what is deliberately left out.

What's on this page

  • What each of the ten services does, and why this stack ships it at all
  • The path a metric, a log line and a span take before Grafana renders them
  • The one flag that decides whether the bundle exists, and how to turn it off
  • Where each component's config lives in the checkout, and what it costs to change
  • Which of the thirteen provisioned dashboards answers which question, and how a panel actually gets changed
  • Retention caps, the named volumes the data lands on, and how to reach each UI
  • What is not here - no pager destination until you set one, no object storage, no trace client

What this enables

  • Reading the box's history from Grafana instead of from docker compose logs
  • Telling a scrape fault from a write fault from a read fault in three commands
  • Deciding what to add next without guessing what is already wired

Ten services sit behind one Compose profile. Six of them store and read - prometheus, mimir, loki, tempo, grafana and alloy - and four watch the box and speak up - node_exporter, cadvisor, blackbox_exporter and alertmanager. They answer one question the rest of the stack cannot - what this box was doing ten minutes ago - and they are the only part of the stack that keeps data after a container is gone. Everything else on this page is about the seams between them, because that is where a monitoring stack silently stops working: a service can be running, a dashboard can be green, and a panel can still be empty.

The split is upstream's own: Prometheus is a fast local scratch store, Mimir is the same PromQL over longer retention, and Alloy is the single agent that touches the host filesystem. This box needs all three because a container that dies takes its own log file out of docker compose logs reach only if you are too late - but a workspace that was slow at 03:00 is unrecoverable without retention.

How the data moves

Four things are worth naming precisely, because each is a place a panel goes empty while every container stays up:

  • Prometheus is the only scraper. Its scrape config targets the apps that publish /metrics - coder:2112 and litellm:4000 - plus the six components that publish their own (prometheus:9090, mimir:8080, loki:3100, tempo:3200, grafana:3000, alloy:12345), the stack host through node_exporter:9101 and cadvisor:8080, Alertmanager itself at alertmanager:9093, and the Spark jobs that reach blackbox_exporter:9115 as their prober.   • Mimir is written to, not scraped from. Prometheus remote_writes to http://mimir:8080/api/v1/push. A query against the prometheus datasource answers from the local TSDB; the mimir datasource answers through http://mimir:8080/prometheus. Those two disagreeing is the diagnostic, not a bug.
  • Alloy, not Loki, reads the disk. Loki has no Docker credential and no host mount. The only container that sees the host's container log directory is Alloy, and it sees it read-only. That directory is ${STACK_DOCKER_LOG_DIR:-/var/lib/docker/containers}, mounted at the same path inside the collector, so a host whose daemon keeps its logs somewhere else (rootless Docker does) needs that key set or the collector tails nothing.
  • Traces arrive over OTLP only, and one client already speaks it. Anything that wants traces in this stack sends OTLP gRPC to tempo:4317. Grafana is the one shipped caller: GF_TRACING_ENABLED points its own exporter at tempo:4317, so the trace viewer has the product's own spans before any workspace emits one. Tempo's metrics_generator then computes span-metrics and service-graph series and remote_writes them back into Prometheus, which is why Prometheus carries --web.enable-remote-write-receiver: without that flag the write is refused with a 404 and the traces dashboard has nothing to plot.

Grafana's four datasources carry fixed UIDs - prometheus (the default), mimir, loki, tempo - and every shipped dashboard references those UIDs, so renaming one in the UI breaks the dashboards that were provisioned against it.

Four things about that wiring are worth knowing before you edit it:

  • The gap alerts select on the job name. HostNodeExporterGap and HostCadvisorGap fire when job="node_exporter" or job="cadvisor" carries no series, which is why the job name is the Compose service name (observability/prometheus/prometheus.yml:142 and :151). Renaming either service without renaming its job makes two alerts permanently quiet, and no test will tell you.
  • The Spark tier is quiet until the boxes are enrolled. Those two jobs read their targets from observability/spark-targets/sparks.json through file_sd_configs, a file the stack host generates and .gitignore:76 keeps out of git. No file means no target groups, which reads as zero Sparks rather than as a broken probe. The boxes' own node_exporter and DCGM exporter are installed on the boxes by scripts/spark-monitor.sh, not by this Compose file.
  • Grafana lists the rules because the datasource says to. The Prometheus datasource is registered alerting: true (observability/grafana/provisioning/datasources/stack.yaml:26); without that flag the rules answer only on Prometheus' own /alerts page and never appear under Alerting -> Rules. Delivery still belongs to Alertmanager.
  • An alert a person builds in Grafana goes to the same Alertmanager. The provisioned contact point is type: alertmanager at http://alertmanager:9093 (observability/grafana/provisioning/alerting/stack.yaml:28), not a webhook, so it speaks /api/v2/alerts and Alertmanager's grouping, inhibition and silences apply to Grafana-originated alerts exactly as they do to Prometheus'. One place holds the silences, whichever engine fired.

Nothing leaves the box until the operator says who to tell. Alertmanager's own config parser cannot expand an environment variable inside a webhook URL, so observability/alertmanager/alertmanager.yml carries no URL at all: all four webhook receivers read url_file: /alertmanager/webhook_url. That file is written at container start by the image's entrypoint, observability/alertmanager/boot-webhook-url.sh, from the ALERTMANAGER_WEBHOOK_URL key (.env.example:635, empty as shipped), and the script then execs the binary. An empty key is a working configuration: the container starts, the rules fire, the receivers are no-ops, and the entrypoint regenerates the file every start so a removed key cannot survive as a stale destination on disk. The Alertmanager UI is loopback-bound for the same reason it has no auth - it can silence alerts - so read it from a shell on the stack host, or use Grafana's Alerting pages, which need no extra port.

The flag

One key decides whether the bundle exists: OBSERVABILITY_ENABLED, default true, in .env.example and .env.sample beside it. All ten services carry profiles: ["observability"], and compose_observability_args() in scripts/lib/common.sh is the single place that reads the key - it prints --profile observability when the value is truthy and nothing for false, 0, no or off. Every stack runner goes through it: dev-stack.sh and prod-stack.sh in their compose_prefix() and run_compose(), and update-stack.sh in stack_compose().

To turn the bundle off, set the key in the env file that belongs to that project - .env for the stable stack, dev-stack.env for the dev one - and bring the stack up:

A profile decides which services a command selects; it does not delete what is already running. The ten containers stay up until you stop them, so after flipping the key off either take the project down (bazelisk run //scripts:prod-stack -- down) or delete the ten by name through compose. Their named volumes survive either way, and reset is the one that destroys them.

Both flag paths are gated: bazelisk run //scripts:validate runs docker compose config -q twice, once plain and once with --profile observability, so a compose file that only parses with the bundle on (or only with it off) fails the build rather than the deploy.

Two consequences of the :ro mounts, both the same rule the other payload directories follow. A bind follows the path, so an edit made in the checkout is already inside the running container, and the only question left is when the process reads it again: and these are directory binds, so measured against the pinned image an in-place rewrite of a mounted file and a rename of a new one over it both reached the container with no restart and no recreate, which is why the dashboards section below can promise a minute rather than a redeploy. The grafana service carries two settings that live in its environment: block (docker-compose.yml:1034-1035) rather than in any file above, each one there to quiet a Grafana 13.3.1 defect this box pays for as log noise. GF_LOG_FILTERS: search-manifest-watcher:error drops that one logger to error and leaves every other logger at its default. The watcher warns twice each poll, and the polls in the log this branch was cut from were 41 to 59 s apart - source listed zero manifests, then zero manifests, keeping previous set - whenever no app publishes a search manifest, which is every OSS install with nothing provisioned into the app platform; upstream calls that a logging defect (grafana/grafana#137058) and confirms search keeps working, because retrying an empty source is intended and only the level is wrong. The filter is a workaround for that defect, not a preference: it comes out when the pin moves to a release carrying the fix, and the pin today is grafana/grafana:13.3.1 (docker-compose.yml:976). GF_UNIFIED_STORAGE_OVERRIDES_PATH: /etc/grafana/stack-overrides.yml points the unified-storage resource server at the file the table names: without it the quota lookup the browse view fires on every dashboard page answers 501, since that server's quota service is nil with nothing pointed at it (grafana/grafana#136271), and the box prints one error line per page load while the browser console fills with 501s; with it the same call answers 200. Both halves were measured on grafana/grafana:13.3.1 as two containers differing only in that variable: the one without the file answered 501 for both dashboard.grafana.app/dashboards and folder.grafana.app/folders and the one with it answered 200 for both, with /api/health 200 either way. On the filter side, over one 300-second window the unfiltered container wrote 16 search-manifest-watcher lines, all level=warn, and the filtered one wrote none from that logger - the only line in it that still names it is Grafana's own level=info record that the setting came from the environment. The overrides file itself says overrides: {}, which is Grafana's own defaults - it is the file's presence that clears the 501, not any limit set in it. What the quota call then reports is that default, {"usage":0,"limit":1000} for dashboards and for folders on 13.3.1; four plausible cap shapes left the number where it was, and a scalar or an unparseable document under overrides: stops the container at boot, so the file's header asks for a limit to be proven on the pinned image before it is written down.

How the Sparks pages reach one machine

evo-sparks-overview and evo-spark-host each declare a host templating variable, both of them a query variable whose query is label_values(spark:box_up, hostname), so the dropdown lists the boxes Prometheus actually sees and nothing else. On evo-spark-host the variable is labelled Spark and every panel on the page filters to whatever it holds.

The overview does not ask you to choose first. Seven stat panels - Spark $host, GPU util, Framebuffer fill, Temp headroom, Power, CPU, Memory - each carry repeat on that same variable with repeatDirection: h, so the strip renders one column per enrolled box. The link panel Open this Spark repeats alongside them and points at /d/evo-spark-host/one-dgx-spark?var-host=${var:queryparam}: the tile under the box you are reading opens that box's page with host already set. That is the path from a red tile on the overview to the GPU rows for that machine, and it is the only link between the two boards. evo-sparks-fleet declares no variable at all, because it aggregates across every box by design.

A dashboard is a committed file

The provider owns the EVO-T1 folder, so nothing you do in the browser to a shipped panel survives: allowUiUpdates: false refuses the save, disableDeletion: true refuses the delete, and the 60-second poll quietly undoes whatever the UI let you stage. A board you build from scratch is not thrown away - it lands in Grafana's own database on grafana-data

  • but it is invisible to git and to the gate below, which is the same drift the :ro mounts above exist to prevent.

So the way to change a panel is to edit its JSON and let the interval apply it. The folder is bind-mounted read-only onto the path the provider scans (docker-compose.yml:1049), so an edit to a file that is already there is visible to the running container and shows up within a minute - no restart, and no recreate. A new file needs no registration either, for the same reason. The gate

The folder is source, so it is tested as source:

tests/bats/observability-dashboards.bats asserts seventeen properties over every file in it: the folder is non-empty and each file parses with the repo's own parser; each is pure ASCII, LF-only, one trailing newline; the pinned top-level keys and house values are present; UIDs and titles are unique across the folder; panel ids are unique integers; every panel carries a full gridPos and no two visible panels overlap; every panel stays inside the house key set; every target opens with refId and carries its own datasource; every datasource is one of the four provisioned UIDs; every querying panel carries a description; every stat states its own empty reading rather than leaving it to Grafana; every referenced variable is declared; every templating variable is well formed; every link names a dashboard that exists in the folder; every UID besides evo-home is named by a link panel or a links: entry there; and no file carries an import block, a host name, or a dead metric shape.

The one to read before you write an expr: every metric name in every expr has to sit on a pinned allow-list, and that list is assembled at test time from the recording rules this repo ships under observability/prometheus/rules/ as well as the pinned names (tests/bats/observability-dashboards.bats:688). A new recording rule therefore needs no test edit, and a metric nothing here records fails the build instead of rendering an empty tile. bazelisk run //scripts:validate covers the coarser layer: it parses every dashboard JSON through scripts/lib/parse_json.py (scripts/validate.sh:104), the gate that already covers the three rule files.

Nothing in this section has been rendered in a live Grafana from this checkout: the pages are proven by that structure and by metric names a source in this repo backs, not by pixels.

Operator checks

Start with the one command that asks all of these at once, then drop to the individual probes when it names a section:

It walks the bundle outward from the dotenv - the operator keys, the host's log directory, the profile render, each container's state, each endpoint, whether data is actually moving - and prints the stack's usual summary: N ok, W warnings, F failed. It is the check that catches the two failures a running state hides: an Alloy pointed at an empty log root, and a Prometheus that scraped everything for a day and never wrote a sample to Mimir. --no-docker skips the four unpublished backends when you are not on a shell that can address the daemon.

Its service list is still the original six (OBS_SERVICES, scripts/observability-check.sh:165). The four exporters and Alertmanager declare no healthcheck and publish no readiness path of their own, so their state comes from the status rows and the container logs below, not from this check.

Are the scrapes up:

Every target should read "health":"up". A target missing entirely is the scrape config; a target present and down is the app not serving /metrics, or - for litellm alone - the bearer file not holding the key the proxy answers with. That failure describes itself twice over: a file that is not there leaves one red target whose lastError names /etc/prometheus-secrets/litellm_token while Prometheus loads the rest of the config normally, and a file holding the wrong key brings LiteLLM

LiteLLM

The single OpenAI-compatible proxy in front of every model, local and remote.

's 401 body No connected db., which at v1.102.1 is the wrong-token branch rather than a database complaint - its auth path compares the bearer against LITELLM_MASTER_KEY and returns PROXY_ADMIN before it looks for a DB. Either way the fix is the file and a recreate of prometheus so Compose renders it again; the metrics stay authenticated. What that 401 offers instead is turning the endpoint's auth off (litellm_settings.require_auth_for_metrics_endpoint), and this stack refuses it: :4000 is published to the LAN, and these metrics name model aliases and traffic volumes.

What is deliberately not here

  • No destination is configured, so nothing pages anyone as shipped. The rules, the routes and the receivers all exist; only the URL is missing. ALERTMANAGER_WEBHOOK_URL is empty in .env.example, so on a box nobody edited every alert is visible - on Prometheus' own alerts page and under Grafana's Alerting pages - and is delivered nowhere. Who gets woken is an operator decision, made in the env file.
  • No healthcheck or dashboard card for the four new services. None of node_exporter, cadvisor, blackbox_exporter or alertmanager declares a healthcheck, and the dashboard's Observability group still carries five cards (dashboard.md), so their liveness is the status row plus the container log.
  • No object storage. Loki, Mimir and Tempo keep blocks on named volumes on this box's disk. The follow-up is a bucket and the storage config in each of those three files; nothing about the read path changes when it lands.
  • No trace client. Tempo has an OTLP door and a datasource, and no caller. Pointing the first service at tempo:4317 is a change in that service, not in this bundle.

When a symptom shows up as an empty panel, start at troubleshooting.md, Observability section: the failures an operator actually hits are all on one side of a seam - the scrape, the write, the tenant path, or the log root Alloy was given.
