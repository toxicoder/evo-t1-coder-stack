Observability bundle

The ten profile-gated monitoring services: what each one does, how metrics, logs and traces reach Grafana, how an alert reaches Alertmanager, where each config file lives, what the data costs on disk, and what is deliberately left out.

What's on this page

  • What each of the ten services does, and why this stack ships it at all
  • The path a metric, a log line and a span take before Grafana renders them
  • The one flag that decides whether the bundle exists, and how to turn it off
  • Where each component's config lives in the checkout, and what it costs to change
  • Which of the thirteen provisioned dashboards answers which question, and how a panel actually gets changed
  • Retention caps, the named volumes the data lands on, and how to reach each UI
  • What is not here - no pager destination until you set one, no object storage, no trace client

What this enables

  • Reading the box's history from Grafana instead of from docker compose logs
  • Telling a scrape fault from a write fault from a read fault in three commands
  • Deciding what to add next without guessing what is already wired

Ten services sit behind one Compose profile. Six of them store and read - prometheus, mimir, loki, tempo, grafana and alloy - and four watch the box and speak up - node_exporter, cadvisor, blackbox_exporter and alertmanager. They answer one question the rest of the stack cannot - what this box was doing ten minutes ago - and they are the only part of the stack that keeps data after a container is gone. Everything else on this page is about the seams between them, because that is where a monitoring stack silently stops working: a service can be running, a dashboard can be green, and a panel can still be empty.

The split is upstream's own:

  • Prometheus is a fast local scratch store
  • Mimir is the same PromQL over longer retention
  • Alloy is the single agent that touches the host filesystem

This box needs all three because a container that dies takes its own log file out of docker compose logs reach only if you are too late - but a workspace that was slow at 03:00 is unrecoverable without retention.

How the data moves

The path each signal takes

Four places a panel goes empty

Four things are worth naming precisely, because each is a place a panel goes empty while every container stays up:

  • Prometheus is the only scraper. Its scrape config targets the apps that publish /metrics - coder:2112 and litellm:4000 - plus:

    • the six components that publish their own (prometheus:9090, mimir:8080, loki:3100, tempo:3200, grafana:3000, alloy:12345)
    • the stack host through node_exporter:9101 and cadvisor:8080
    • Alertmanager itself at alertmanager:9093
    • the Spark jobs that reach blackbox_exporter:9115 as their prober

The four fixed datasource UIDs

Grafana's four datasources carry fixed UIDs - prometheus (the default), mimir, loki, tempo - and every shipped dashboard references those UIDs, so renaming one in the UI breaks the dashboards that were provisioned against it.

Four things to know before editing the wiring

Four things about that wiring are worth knowing before you edit it:

  • The gap alerts select on the job name. HostNodeExporterGap and HostCadvisorGap fire when job="node_exporter" or job="cadvisor" carries no series, which is why the job name is the Compose service name (observability/prometheus/prometheus.yml:142 and :151). Renaming either service without renaming its job makes two alerts permanently quiet, and no test will tell you.
  • The Spark tier is quiet until the boxes are enrolled. Those two jobs read their targets from observability/spark-targets/sparks.json through file_sd_configs, a file the stack host generates and .gitignore:76 keeps out of git. No file means no target groups, which reads as zero Sparks rather than as a broken probe. The boxes' own node_exporter and DCGM exporter are installed on the boxes by scripts/spark-monitor.sh, not by this Compose file.
  • Grafana lists the rules because the datasource says to. The Prometheus datasource is registered alerting: true (observability/grafana/provisioning/datasources/stack.yaml:26); without that flag the rules answer only on Prometheus' own /alerts page and never appear under Alerting -> Rules. Delivery still belongs to Alertmanager.
  • An alert a person builds in Grafana goes to the same Alertmanager. The provisioned contact point is type: alertmanager at http://alertmanager:9093 (observability/grafana/provisioning/alerting/stack.yaml:28), not a webhook, so it speaks /api/v2/alerts and Alertmanager's grouping, inhibition and silences apply to Grafana-originated alerts exactly as they do to Prometheus'. One place holds the silences, whichever engine fired.

The webhook destination is empty as shipped

Nothing leaves the box until the operator says who to tell.

Alertmanager's own config parser cannot expand an environment variable inside a webhook URL, so observability/alertmanager/alertmanager.yml carries no URL at all: all four webhook receivers read url_file: /alertmanager/webhook_url.

That file is written at container start by the image's entrypoint, observability/alertmanager/boot-webhook-url.sh, from the ALERTMANAGER_WEBHOOK_URL key (.env.example:635, empty as shipped), and the script then execs the binary.

An empty key is a working configuration: the container starts, the rules fire, the receivers are no-ops, and the entrypoint regenerates the file every start so a removed key cannot survive as a stale destination on disk.

The Alertmanager UI is loopback-bound for the same reason it has no auth - it can silence alerts - so read it from a shell on the stack host, or use Grafana's Alerting pages, which need no extra port.

The flag

One key decides whether the bundle exists: OBSERVABILITY_ENABLED, default true, in .env.example and .env.sample beside it.

All ten services carry profiles: ["observability"], and compose_observability_args() in scripts/lib/common.sh is the single place that reads the key - it prints --profile observability when the value is truthy and nothing for false, 0, no or off.

Every stack runner goes through it:

  • dev-stack.sh and prod-stack.sh in their compose_prefix() and run_compose()
  • update-stack.sh in stack_compose()

Turning the bundle off

To turn the bundle off, set the key in the env file that belongs to that project - .env for the stable stack, dev-stack.env for the dev one - and bring the stack up:

A profile decides which services a command selects; it does not delete what is already running. The ten containers stay up until you stop them, so after flipping the key off either take the project down (bazelisk run //scripts:prod-stack -- down) or delete the ten by name through compose.

Their named volumes survive either way, and reset is the one that destroys them.

Both flag paths are gated

Both flag paths are gated: bazelisk run //scripts:validate runs docker compose config -q twice, once plain and once with --profile observability, so a compose file that only parses with the bundle on (or only with it off) fails the build rather than the deploy.

What the read-only mounts mean

Two consequences of the :ro mounts, both the same rule the other payload directories follow:

  • A bind follows the path, so an edit made in the checkout is already inside the running container, and the only question left is when the process reads it again
  • These are directory binds, so measured against the pinned image an in-place rewrite of a mounted file and a rename of a new one over it both reached the container with no restart and no recreate, which is why the dashboards section below can promise a minute rather than a redeploy

The one credential that behaves differently is the LiteLLM

 bearer token, and the reason is that it is not a bind - Compose writes a configs entry when it creates the container, so rotating LITELLM_MASTER_KEY takes up -d --force-recreate prometheus, where a plain up -d leaves the old bytes in place, and so does a restart.

And treat the provisioned dashboards and datasources as read-only in the UI: allowUiUpdates: false and disableDeletion: true stop a save from overwriting the JSON, so anything you build by hand lands in Grafana's own database in grafana-data instead - it works, and it drifts from git invisibly.

The two Grafana environment settings

The grafana service carries two settings that live in its environment: block (docker-compose.yml:1034-1035) rather than in any file above, each one there to quiet a Grafana 13.3.1 defect this box pays for as log noise.

The search-manifest-watcher filter

GF_LOG_FILTERS: search-manifest-watcher:error drops that one logger to error and leaves every other logger at its default.

The watcher warns twice each poll, and the polls in the log this branch was cut from were 41 to 59 s apart - source listed zero manifests, then zero manifests, keeping previous set - whenever no app publishes a search manifest, which is every OSS install with nothing provisioned into the app platform; upstream calls that a logging defect (grafana/grafana#137058) and confirms search keeps working, because retrying an empty source is intended and only the level is wrong.

The filter is a workaround for that defect, not a preference: it comes out when the pin moves to a release carrying the fix, and the pin today is grafana/grafana:13.3.1 (docker-compose.yml:976).

The unified-storage overrides file

GF_UNIFIED_STORAGE_OVERRIDES_PATH: /etc/grafana/stack-overrides.yml points the unified-storage resource server at the file the table names: without it the quota lookup the browse view fires on every dashboard page answers 501, since that server's quota service is nil with nothing pointed at it (grafana/grafana#136271), and the box prints one error line per page load while the browser console fills with 501s; with it the same call answers 200.

Both halves were measured on grafana/grafana:13.3.1 as two containers differing only in that variable: the one without the file answered 501 for both dashboard.grafana.app/dashboards and folder.grafana.app/folders and the one with it answered 200 for both, with /api/health 200 either way.

On the filter side, over one 300-second window the unfiltered container wrote 16 search-manifest-watcher lines, all level=warn, and the filtered one wrote none from that logger - the only line in it that still names it is Grafana's own level=info record that the setting came from the environment.

The overrides file itself says overrides: {}, which is Grafana's own defaults - it is the file's presence that clears the 501, not any limit set in it.

What the quota call then reports is that default, {"usage":0,"limit":1000} for dashboards and for folders on 13.3.1; four plausible cap shapes left the number where it was, and a scalar or an unparseable document under overrides: stops the container at boot, so the file's header asks for a limit to be proven on the pinned image before it is written down.

A dashboard is a committed file

The provider owns the EVO-T1 folder, so nothing you do in the browser to a shipped panel survives: allowUiUpdates: false refuses the save, disableDeletion: true refuses the delete, and the 60-second poll quietly undoes whatever the UI let you stage.

A board you build from scratch is not thrown away - it lands in Grafana's own database on grafana-data - but it is invisible to git and to the gate below, which is the same drift the :ro mounts above exist to prevent.

So the way to change a panel is to edit its JSON and let the interval apply it. The folder is bind-mounted read-only onto the path the provider scans (docker-compose.yml:1049), so an edit to a file that is already there is visible to the running container and shows up within a minute - no restart, and no recreate. A new file needs no registration either, for the same reason.

Recreate only when the mount line or the provisioning tree itself changed (docker-compose.yml:1047-1048), and then with the up -d rule from the section above:

The gate

The folder is source, so it is tested as source:

tests/bats/observability-dashboards.bats asserts seventeen properties over every file in it:

  • the folder is non-empty and each file parses with the repo's own parser
  • each is pure ASCII, LF-only, one trailing newline
  • the pinned top-level keys and house values are present
  • UIDs and titles are unique across the folder
  • panel ids are unique integers
  • every panel carries a full gridPos and no two visible panels overlap
  • every panel stays inside the house key set
  • every target opens with refId and carries its own datasource
  • every datasource is one of the four provisioned UIDs
  • every querying panel carries a description
  • every stat states its own empty reading rather than leaving it to Grafana
  • every referenced variable is declared
  • every templating variable is well formed
  • every link names a dashboard that exists in the folder
  • every UID besides evo-home is named by a link panel or a links: entry there
  • no file carries an import block, a host name, or a dead metric shape

The metric allow-list

The one to read before you write an expr: every metric name in every expr has to sit on a pinned allow-list, and that list is assembled at test time from the recording rules this repo ships under observability/prometheus/rules/ as well as the pinned names (tests/bats/observability-dashboards.bats:688).

A new recording rule therefore needs no test edit, and a metric nothing here records fails the build instead of rendering an empty tile.

The coarser gate

bazelisk run //scripts:validate covers the coarser layer: it parses every dashboard JSON through scripts/lib/parse_json.py (scripts/validate.sh:104), the gate that already covers the three rule files.

Nothing in this section has been rendered in a live Grafana from this checkout: the pages are proven by that structure and by metric names a source in this repo backs, not by pixels.

Changing a cap

Change a cap in the env file and recreate. The Prometheus size cap is the one that actually bounds the box: it is the only figure that does not depend on how fast the series arrive.

Tempo's cap is the odd one, because Tempo 3.x moved it out of the config file - it reaches the container as -backend-scheduler.provider.work.compaction.block-retention on the command line in docker-compose.yml, so editing tempo.yml for it changes nothing.

bazelisk run //scripts:storage-clean is the interactive janitor for the persistent layer if a volume outgrows what you meant it to hold.

Operator checks

The one command that asks all of these

Start with the one command that asks all of these at once, then drop to the individual probes when it names a section:

It walks the bundle outward from the dotenv - the operator keys, the host's log directory, the profile render, each container's state, each endpoint, whether data is actually moving - and prints the stack's usual summary: N ok, W warnings, F failed.

It is the check that catches the two failures a running state hides: an Alloy pointed at an empty log root, and a Prometheus that scraped everything for a day and never wrote a sample to Mimir.

--no-docker skips the four unpublished backends when you are not on a shell that can address the daemon.

What that check does not cover

Its service list is still the original six (OBS_SERVICES, scripts/observability-check.sh:165). The four exporters and Alertmanager declare no healthcheck and publish no readiness path of their own, so their state comes from the status rows and the container logs below, not from this check.

The probes, in order

Then, from the checkout on the stack host, in this order. Each one splits one symptom from the next.

Is the bundle selected at all

Ten rows when OBSERVABILITY_ENABLED is on, none when it is off.

Expect running, not healthy, on the eight that declare no healthcheck: mimir, loki, tempo and alloy (those four images are distroless, so they carry no shell and no wget/curl for a healthcheck to run), plus node_exporter, cadvisor, blackbox_exporter and alertmanager. Only prometheus and grafana declare one.

A missing row means the profile was not selected - see the troubleshooting entry on which env file the dev project actually reads.

Did Grafana come up and can it read its own database

Are the scrapes up

Every target should read "health":"up". A target missing entirely is the scrape config; a target present and down is the app not serving /metrics, or - for litellm alone - the bearer file not holding the key the proxy answers with.

That failure describes itself twice over: a file that is not there leaves one red target whose lastError names /etc/prometheus-secrets/litellm_token while Prometheus loads the rest of the config normally, and a file holding the wrong key brings LiteLLM

LiteLLM

The single OpenAI-compatible proxy in front of every model, local and remote.

's 401 body No connected db., which at v1.102.1 is the wrong-token branch rather than a database complaint - its auth path compares the bearer against LITELLM_MASTER_KEY and returns PROXY_ADMIN before it looks for a DB.

Either way the fix is the file and a recreate of prometheus so Compose renders it again; the metrics stay authenticated.

What that 401 offers instead is turning the endpoint's auth off (litellm_settings.require_auth_for_metrics_endpoint), and this stack refuses it: :4000 is published to the LAN, and these metrics name model aliases and traffic volumes.

Is the write to Mimir landing

A refused or failing remote_write shows up in the Prometheus log.

The clean version of the same question is asked in the UI: the prometheus datasource has the series and the mimir one does not, which is a write fault, not a query fault.

Are the three unpublished backends alive

Their health endpoints are http://loki:3100/ready, http://tempo:3200/ready and http://mimir:8080/ready, all compose-DNS only.

Those exact URLs are the siteMonitor of the Observability group's cards on the dashboard, so the card badge is the probe - and because those four containers have no healthcheck, it is the only automatic one.

For the logs behind a red badge, use the container log rather than an exec, since a distroless image has no shell to exec into:

Is the whole thing still well-formed on both flag paths

That gate is what makes the monitoring payloads ordinary source: it parses the three rule files, alertmanager.yml, blackbox.yml and the Grafana alerting policy, and parses every dashboard JSON through scripts/lib/parse_json.py (scripts/validate.sh:104).

A panel that is not well-formed JSON, a dashboard whose title is blank, and the generated Spark file-SD document are gate failures now rather than an empty tile someone notices in the browser.

Asking the plane from a shell

Everything above is written for someone standing at the UI on :3005. A coding agent has no browser and no admin login, and the walls that keep a person out keep an agent out harder: loki, mimir and tempo publish no host port at all, prometheus and alertmanager bind the stack host's 127.0.0.1, and Grafana - the one published surface - answers only to a credential.

The door is one CLI, and it is read-only end to end:

scripts/observability-query.sh is this page's scripts/observability-check.sh counterpart: that one proves the bundle is wired, this one asks it questions. Every query goes to a provisioned datasource by UID through Grafana's datasource proxy (/api/datasources/proxy/uid/<uid>/...), so the query language is the one the panel already uses and the read-only service-account token is the only credential involved. The backends that need no credential and bind loopback are reached with a one-shot curlimages/curl:8.10.1 container on ${PROJECT_NAME}_default - the same transport scripts/observability-check.sh:454 uses, and the only transport that works from a workspace container, which cannot see the host's loopback. --no-docker switches that verb to the host's own loopback, for a run in a host shell.

The verbs, and one call each

Six ways to ask. All of them take --since (default 1h; a whole number with s, m, h or d), --limit (default 50, capped at 500, whole number above zero), --timeout (default 5 s, whole number above zero - 0 and 00 are refused, because both would lift the cap rather than set it), and --json, which sends the payload alone to stdout and every report line to stderr - the channel a machine parses.

Where Grafana answers is configuration, never a hard-coded dial: --base-url, then the GRAFANA_URL key, then GRAFANA_BASE_URL (both read from the environment, then the dotenv), then the loopback default http://127.0.0.1:$GRAFANA_PORT. That order is what makes the same CLI work from the two places it is run. A host shell takes the default. A workspace container does not: host loopback is unreachable from inside it, so from there point it at the LAN origin or at http://host.docker.internal:<GRAFANA_PORT> (--base-url http://host.docker.internal:3005, or GRAFANA_BASE_URL in the env the agent runs with). The value is checked before the first request - an origin, not a path, query, or credentials - and the report line names which knob answered.

search TERM - Grafana's /api/search?query=TERM: dashboards, folders, panels and datasources that match. This is the verb that finds the UID or panel title a sharper question needs.

dashboards - /api/search?type=dash-db: what the file provider actually registered. A JSON committed under observability/grafana/dashboards/ is not a screen until this answers for it, so "the dashboard is missing" is a dashboards question, not a browser question.

logs QUERY - LogQL over the loki datasource (observability/grafana/provisioning/ datasources/stack.yaml:46), as a range query over the window. QUERY is one LogQL expression in single quotes.

metrics QUERY - PromQL over the prometheus datasource (observability/grafana/provisioning/datasources/stack.yaml:15), which is the datasource the shipped panels use. --source mimir runs the identical string against observability/grafana/provisioning/datasources/stack.yaml:32 instead, and that is the only thing that changes; reach for it when the window is past Prometheus' retention.

--step adds a range step; without it Prometheus returns one point per series, which is what a "what is up right now" question wants.

alerts - Alertmanager's /api/v2/alerts, from inside the project network. Alertmanager needs no token, so this is the one verb that works before anyone has minted one.

--self-test - proves the token authenticates and that each of the four provisioned datasources answers through the proxy, by asking each for its label names. It pulls back no sample and prints no payload, so it is the line to paste into a transcript. It takes no verb.

The four labels, and why a fifth is refused

A LogQL selector may filter on exactly four labels - container, stream, job, stack - the whitelist at scripts/lib/observability_query.sh:34:

  • container is the compose log tag, which Alloy lifts out of each json-file line (observability/alloy/config.alloy:71, with one options: { tag: ... } per service, e.g. docker-compose.yml:263 for litellm). The set of valid values is the set of tags in docker-compose.yml, nothing more and nothing less.
  • stream is the json-file driver's own field, stdout or stderr (observability/alloy/config.alloy:72).
  • job is docker and stack is evo-t1, both stamped on at discovery (observability/alloy/config.alloy:35-36).

A selector naming any other label is refused before the first request, with exit 2 and the allowed set printed back (obsq_logql_rejects at scripts/lib/observability_query.sh:142, enforced at scripts/observability-query.sh:960-964). It is not ignored, and not because an unknown label is expensive: Loki never carried that label, so the query cannot fail, it can only come back empty - and an empty result is the exact shape of "this box has no logs", which is the one answer an agent must never be handed by a typo. {service="litellm"} and {container="litellm"} look the same to type and mean completely different things.

What the check does not touch is the part after the pipe: |~ "error", !=, =~ and !~ there compare the line's own text and are not labels, so any filter text is allowed (obsq_logql_label_names, scripts/lib/observability_query.sh:100-125). A query also has to be printable ASCII (scripts/observability-query.sh:955-958): a multibyte or control byte in it is a quoting mistake at the call site, and a newline in a query is a header injection waiting for the wrong transport.

The four answers, and what each one means next

Every verb answers one of four shapes (obsq_answer_shape in scripts/lib/observability_query.sh), and the whole point of the split is that the first three must never collapse into each other:

answerwhat happenedwhat the next step isexit
offthe observability compose profile key says the bundle was never started, and no request was made at allask the operator to bring it up; the report line names OBSERVABILITY_ENABLED and //scripts:dev-stack -- up. Nothing was asked, so nothing is claimed about the bundle0
nodatathe query was accepted and this window or filter matched no row - the only answer allowed to say nothing here is brokenwiden --since, drop a filter, then suspect the writer: the scrape, the remote_write, or Alloy's log root0
errora query, a credential or the transport failed - a 4xx/5xx, a timeout, a dead backend, or an endpoint that could not be reached at allread the line: it names the URL, the code and the token path, and for a refused socket the base-URL knob that answered. Fix that, then re-run1
datarows came backcheck the count against --limit before concluding you saw everything0

off is decided once, before the first request, from the one seam that owns the profile (profile_switched_off calls compose_observability_args) - and from nothing else. A refused socket is error, not off: a connection that reached nothing cannot say whether the profile is on, and from a workspace container the usual cause is the base URL, not the bundle. An all-clear for a query that reached nothing is the failure this split exists to kill, so nothing here is broken is printed only where the bundle actually answered and matched no row. A 401 or a 403 is deliberately not off either - something is listening and it is refusing the credential, which is a fault with a fix.

The mistake this exists to prevent is an agent that gets nodata, prints "no logs found", and moves on while the answer was off: the profile was never up and no log exists to find. bazelisk run //scripts:prod-stack -- status answers the same question from the other side, and costs no credential.

The token: one file, one read, never printed

The credential is a read-only Grafana service-account token, and the CLI takes it from a file and nowhere else (scripts/observability-query.sh:170):

  • default /var/lib/evo-t1-observability/grafana-query-token, overridable with GRAFANA_QUERY_TOKEN_FILE or --token-file
  • scripts/grafana-agent-token.sh mints it and writes that file: one line, one token, mode 0600, readable by the agent user only, on the named volume. That step is what scripts/observability-query.sh:360 and :363 tell you has not run when the file is unreadable or holds something that is not one token-shaped line (obsq_read_token, which refuses a value carrying a CR or LF rather than forwarding an injectable second header)
  • it never enters argv, so it never reaches a process listing, a shell history line, or a test stub's argv log; it reaches curl through a --config file written under umask 077, not -H
  • it is never printed, and every string the CLI prints - the report lines, curl's complaint, and the response body - passes through obsq_redact first, because a log line is free to quote the request that wrote it and a token that comes back in a body is still a token

So: never copy the token into a command, a flag, a URL, an issue, a commit, or a reply. Name its path, which is the thing an operator can act on. A missing token is an error and not off, precisely because the profile check already answered "never enabled" - a box that is enabled and has no credential has a boot step that did not run.

Minting it: scripts/grafana-agent-token.sh

Nothing file-provisions this credential, and nothing can. Grafana file-provisions datasources, dashboards and alerting - the three trees mounted at docker-compose.yml:1089-1090 - while a service account is a row in its database and a token is a secret generated at creation time: there is no provisioning schema for either, and a token checked into observability/ would be a committed credential, which this stack never ships. So the account and its token are created through the same API the console uses.

In order, and each one is a thing the CLI will not let you skip:

  1. it refuses before anything else unless the write is the one the operator asked for (gat_refuses_overwrite). A target that already holds a live credential is refused without --rotate: rotation is never a side effect of re-running setup. A target that is absent or holds nothing token-shaped is refused without --repair, because this path (/var/lib/evo-t1-observability/grafana-query-token) is box-wide and read by every agent on the box - establishing a credential there is an act, not a fall-out. --dry-run prints what the missing file means instead of refusing.
  2. it reuses the service account evo-t1-agent, or creates it with role Viewer. The role is a constant in the script, not a flag, so there is no way to ask for an editor, and a role the answer disagrees with is a failure rather than a warning (gat_ensure_service_account). Then, every run and not only under --rotate, it revokes the account's tokens that this CLI's own naming scheme owns (${ACCOUNT_NAME}-token, or that name with a -<n> suffix - gat_token_name_owned), so ten reruns leave one live credential behind instead of ten, while a token another tool minted against the same account is left alone.
  3. it validates the answer before it writes: one line, the alphabet obsq_read_token accepts, nothing else - a truncated response or a whole body fails and leaves the previous credential in place (gat_write_token_file).
  4. it writes the path, mode 0600, and keeps the value out of everything else. The admin credential travels in a curl --config file and both bodies behind a bind mount of a 0700 scratch directory, so nothing credential-shaped is ever an argument to docker or to curl, and every string the CLI prints is scrubbed by gat_redact. --help and --dry-run answer with no docker and no request at all.

The mint has a lifetime by default: 30 days (2592000 s), changed with --ttl SECONDS or the GRAFANA_AGENT_TOKEN_TTL key and refused unless it is a whole number above zero. A credential that outlives its operator is the thing this defaults against, so the endless token is an explicit opt-in - --no-expiry, which conflicts with --ttl and prints a warning: line saying so when it is used.

The request is made the way the rest of the bundle reaches the plane: a one-shot curlimages/curl:8.10.1 container on ${PROJECT_NAME}_default calling http://grafana:3000 (scripts/observability-check.sh:454 is the same transport), so a box where GRAFANA_PORT is taken mints just the same. The token is never printed, in any mode, and never taken back: to change it, re-run with --rotate.

The path to follow when something is broken

Work outward from what exists, and stop at the first answer that explains the symptom:

logs filtered by container= before anything else is the step that pays: it is the label the pipeline guarantees, it is the one every shipped log panel filters on, and it narrows a whole host down to one service in one request. Then ask the same window of metrics - a log line with no matching series is a scrape problem, and a series with no matching log line is usually the container not the app. --source mimir on step 4 is how you ask "did this start before Prometheus still remembers".

Print the command you ran and the line it said, one at a time, rather than firing all five and reading the wall.

Read-only, all of it

Every verb above is a read: a range query, a search, or an alert list. There is no verb that creates, edits, moves or deletes a dashboard, a folder, a datasource, a rule, or a receiver - and the plane itself refuses that even to the admin UI: the provisioned folder is mounted with disableDeletion: true (observability/grafana/provisioning/dashboards/stack.yaml:16), so a dashboard that exists here came from a committed file and comes back on the next reload. A panel an agent "fixes" in the browser is unfixable in the only place that matters: the JSON under observability/grafana/dashboards/, which the gate parses (scripts/validate.sh:104). Change the file, or say what needs changing.

What is deliberately not here

  • No destination is configured, so nothing pages anyone as shipped. The rules, the routes and the receivers all exist; only the URL is missing. ALERTMANAGER_WEBHOOK_URL is empty in .env.example, so on a box nobody edited every alert is visible - on Prometheus' own alerts page and under Grafana's Alerting pages - and is delivered nowhere.

    Who gets woken is an operator decision, made in the env file.

  • No healthcheck or dashboard card for the four new services. None of node_exporter, cadvisor, blackbox_exporter or alertmanager declares a healthcheck, and the dashboard's Observability group still carries five cards (dashboard.md), so their liveness is the status row plus the container log.

  • No object storage. Loki, Mimir and Tempo keep blocks on named volumes on this box's disk. The follow-up is a bucket and the storage config in each of those three files; nothing about the read path changes when it lands.

  • No trace client. Tempo has an OTLP door and a datasource, and no caller. Pointing the first service at tempo:4317 is a change in that service, not in this bundle.

When a symptom shows up as an empty panel, start at troubleshooting.md, Observability section: the failures an operator actually hits are all on one side of a seam:

  • the scrape
  • the write
  • the tenant path
  • the log root Alloy was given
