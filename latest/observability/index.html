Observability bundle

The six profile-gated monitoring services: what each one does, how metrics, logs and traces reach Grafana, where each config file lives, what the data costs on disk, and what is deliberately left out.

What's on this page

  • What each of the six services does, and why this stack ships it at all
  • The path a metric, a log line and a span take before Grafana renders them
  • The one flag that decides whether the bundle exists, and how to turn it off
  • Where each component's config lives in the checkout, and what it costs to change
  • Retention caps, the named volumes the data lands on, and how to reach each UI
  • What is not here - no Alertmanager, no host or container exporter, no object storage

What this enables

  • Reading the box's history from Grafana instead of from docker compose logs
  • Telling a scrape fault from a write fault from a read fault in three commands
  • Deciding what to add next without guessing what is already wired

Six services sit behind one Compose profile: prometheus, mimir, loki, tempo, grafana and alloy. They answer one question the rest of the stack cannot - what this box was doing ten minutes ago - and they are the only part of the stack that keeps data after a container is gone. Everything else on this page is about the seams between them, because that is where a monitoring stack silently stops working: a service can be running, a dashboard can be green, and a panel can still be empty.

The six services

ServiceImageJob on this box
prometheusprom/prometheus:v3.16.0Scrape. Holds the last PROMETHEUS_RETENTION_TIME of series on its own TSDB and copies every sample to Mimir.

tempografana/tempo:3.1.1Trace store. Listens for OTLP on 4317 and answers trace queries on 3200.
grafanagrafana/grafana:13.3.1The only read path and the only published UI. Metrics, logs and traces all render here, from four provisioned datasources.
alloygrafana/alloy:v1.22.0The collector. Tails the host's Docker json-file logs and pushes them to Loki.

The split is upstream's own: Prometheus is a fast local scratch store, Mimir is the same PromQL over longer retention, and Alloy is the single agent that touches the host filesystem. This box needs all three because a container that dies takes its own log file out of docker compose logs reach only if you are too late - but a workspace that was slow at 03:00 is unrecoverable without retention.

How the data moves

Four things are worth naming precisely, because each is a place a panel goes empty while every container stays up:

  • Prometheus is the only scraper. Its scrape config targets the apps that publish /metrics - coder:2112 and litellm:4000 - plus the six components that publish their own (prometheus:9090, mimir:8080, loki:3100, tempo:3200, grafana:3000, alloy:12345). The LiteLLM

     endpoint is; the key arrives in Prometheus' own environment and is expanded there, which is why it is not written into the committed scrape file.
  • Mimir is written to, not scraped from. Prometheus remote_writes to http://mimir:8080/api/v1/push. A query against the prometheus datasource answers from the local TSDB; the mimir datasource answers through http://mimir:8080/prometheus. Those two disagreeing is the diagnostic, not a bug.
  • Alloy, not Loki, reads the disk. Loki has no Docker credential and no host mount. The only container that sees the host's container log directory is Alloy, and it sees it read-only. That directory is ${STACK_DOCKER_LOG_DIR:-/var/lib/docker/containers}, mounted at the same path inside the collector, so a host whose daemon keeps its logs somewhere else (rootless Docker does) needs that key set or the collector tails nothing.
  • Traces arrive over OTLP only, and one client already speaks it. Anything that wants traces in this stack sends OTLP gRPC to tempo:4317. Grafana is the one shipped caller: GF_TRACING_ENABLED points its own exporter at tempo:4317, so the trace viewer has the product's own spans before any workspace emits one. Tempo's metrics_generator then computes span-metrics and service-graph series and remote_writes them back into Prometheus, which is why Prometheus carries --web.enable-remote-write-receiver: without that flag the write is refused with a 404 and the traces dashboard has nothing to plot.

Grafana's four datasources carry fixed UIDs - prometheus (the default), mimir, loki, tempo - and every shipped dashboard references those UIDs, so renaming one in the UI breaks the dashboards that were provisioned against it.

The flag

One key decides whether the bundle exists: OBSERVABILITY_ENABLED, default true, in .env.example and .env.sample beside it. All six services carry profiles: ["observability"], and compose_observability_args() in scripts/lib/common.sh is the single place that reads the key - it prints --profile observability when the value is truthy and nothing for false, 0, no or off. Every stack runner goes through it: dev-stack.sh and prod-stack.sh in their compose_prefix() and run_compose(), and update-stack.sh in stack_compose().

To turn the bundle off, set the key in the env file that belongs to that project - .env for the stable stack, dev-stack.env for the dev one - and bring the stack up:

A profile decides which services a command selects; it does not delete what is already running. The six containers stay up until you stop them, so after flipping the key off either take the project down (bazelisk run //scripts:prod-stack -- down) or delete the six by name through compose. Their named volumes survive either way, and reset is the one that destroys them.

Both flag paths are gated: bazelisk run //scripts:validate runs docker compose config -q twice, once plain and once with --profile observability, so a compose file that only parses with the bundle on (or only with it off) fails the build rather than the deploy.

Where each config lives

The bundle's payloads are one directory of their own, bind-mounted read-only, so git diff is the record of every monitoring change and nothing is edited in the running container:

Two consequences of the :ro mounts, both the same rule the other payload directories follow: edit the checkout and recreate the service (up -d, not restart, since a restart keeps the old mounts), and treat the provisioned dashboards and datasources as read-only in the UI. allowUiUpdates: false and disableDeletion: true stop a save from overwriting the JSON, so anything you build by hand lands in Grafana's own database in grafana-data instead - it works, and it drifts from git invisibly.

Retention and disk

Everything lands on named volumes under Docker's volume root on the host disk. Nothing here reaches an object store, so the caps are what protect that disk:

ComponentCap (env key, default)Volume -> container path
PrometheusPROMETHEUS_RETENTION_TIME (15d), PROMETHEUS_RETENTION_SIZE (10GB) - whichever hits firstprometheus-data -> /prometheus
MimirMIMIR_RETENTION_PERIOD (2160h, 90 days)mimir-data -> /data/mimir
LokiLOKI_RETENTION_PERIOD (168h, 7 days)loki-data -> /loki
TempoTEMPO_BLOCK_RETENTION_TIME (168h), applied by the backend-scheduler's compaction worktempo-data -> /var/tempo
Grafanan/a (dashboards, not series)grafana-data -> /var/lib/grafana
Alloynone shipped; it keeps its own state under --storage.pathalloy-data -> /var/lib/alloy/data

Change a cap in the env file and recreate. The Prometheus size cap is the one that actually bounds the box: it is the only figure that does not depend on how fast the series arrive. Tempo's cap is the odd one, because Tempo 3.x moved it out of the config file - it reaches the container as -backend-scheduler.provider.work.compaction.block-retention on the command line in docker-compose.yml, so editing tempo.yml for it changes nothing. bazelisk run //scripts:storage-clean is the interactive janitor for the persistent layer if a volume outgrows what you meant it to hold.

Operator checks

Start with the one command that asks all of these at once, then drop to the individual probes when it names a section:

It walks the bundle outward from the dotenv - the operator keys, the host's log directory, the profile render, each container's state, each endpoint, whether data is actually moving - and prints the stack's usual summary: N ok, W warnings, F failed. It is the check that catches the two failures a running state hides: an Alloy pointed at an empty log root, and a Prometheus that scraped everything for a day and never wrote a sample to Mimir. --no-docker skips the four unpublished backends when you are not on a shell that can address the daemon.

What is deliberately not here

  • No Alertmanager, and no rules. The payload tree has no rules directory and prometheus.yml declares no rule_files: block, so nothing evaluates an alert and nothing pages anybody: a fault is visible only when someone opens a dashboard or a card badge goes down. The follow-up is one more service plus its receivers, and the rule files that decide what is worth waking anyone for.
  • No node-exporter and no cAdvisor. Host CPU, memory, temperature and disk stay the dashboard's /proc widgets, and there is no per-container metric source. The follow-up is the two exporters plus the two dashboards that would use them - and host filesystems are exactly the thing the retention caps above are supposed to protect, so an exporter that reads the host needs the same care Alloy got.
  • No object storage. Loki, Mimir and Tempo keep blocks on named volumes on this box's disk. The follow-up is a bucket and the storage config in each of those three files; nothing about the read path changes when it lands.
  • No trace client. Tempo has an OTLP door and a datasource, and no caller. Pointing the first service at tempo:4317 is a change in that service, not in this bundle.

When a symptom shows up as an empty panel, start at troubleshooting.md, Observability section: the failures an operator actually hits are all on one side of a seam - the scrape, the write, the tenant path, or the log root Alloy was given.
