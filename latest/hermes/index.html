 Agent running as the interactive assistant on the stack host itself: not inside a workspace, not in a streamed desktop, but with the checkout, the compose project and the docker socket in reach.

It adds an official Web Dashboard with a Chat tab that carries approval prompts, so the assistant can plan a change, show the plan, and wait for you to approve it before it touches anything.

That is the whole point of the service: stack ops by conversation.

  • "Recreate the dev stack and tell me which container restarts"
  • "why is the coder agent offline"
  • "run the gate and fix what it reports"

Each one runs with a plan first and an approval card before the mutating command.

From the host terminal

The Chat tab is the door for someone at a browser. The terminal door is for someone already on the box, and it opens the same assistant - same SOUL.md, same seeded config.yaml, same git-tracked skills, same LiteLLM

Subcommands and options

  • Subcommands: chat (the default), ask TEXT for one question and exit, shell for a shell with the container's mounts and socket, check for the readiness report, commands for the assistant's own help. Every word after the subcommand is handed to the assistant verbatim, so a flag this script has never heard of still works.
  • Options (before the subcommand): -p/--project-name (evo-t1-prod; the dev sandbox is evo-t1-dev), -f/--file, -e/--env-file, -m/--model <alias> for one session, -w/--writable <dir>, --one-shot, --dry-run, -h/--help.

One container, not two

  • It enters the running container rather than starting a second one. Hermes

    Hermes

    The Nous Research host assistant, with the Web Dashboard and its approval prompts.

     keeps its sessions and memory in a SQLite store under /opt/data, and two containers on one data directory is the documented way to corrupt it - the WAL sidecars and the lock only mean something inside one container.

    So while the gateway is up this is docker compose exec, and the terminal agent and the dashboard agent are literally the same process on the same store. Only when nothing is running does it docker compose run --rm --no-deps a lone container. --one-shot forces the second container anyway and says out loud what it risks.

check, the approval gate, and the tty

  • check is the first thing to run when an answer looks impossible. It reports:

    • the daemon, the compose CLI, the project, the container state
    • whether the service resolves, the image
    • whether the data volume is seeded, whether the model key is set or still a shipped placeholder
    • whether LiteLLM

      LiteLLM

      The single OpenAI-compatible proxy in front of every model, local and remote.

       answers /health/liveliness, the work directory

    It prints key names and never a value, and it launches nothing.

  • Approvals are the same gate, inline. A dangerous command stops in your tty with [o]nce | [s]ession | [a]lways | [d]eny, deny by default.

    There is no browser card here and nothing to approve elsewhere; the terminal door does not loosen approvals.mode: manual, and --yolo / HERMES_YOLO_MODE have no place in this stack. See Approvals.

  • An interactive session needs a real tty (the TUI draws on a pty compose allocates from your terminal), so chat and shell refuse from a pipe or a cron line - that is what ask is for.

What it can see, and where it may write

  • What it can see: the checkout at $STACK_HOST_PATH, the deploy workspace at ${STACK_DEPLOY_PATH:-/opt/stack-deploy}, /opt/stack-skills, the data volume, and the docker socket.

    What it cannot: /home is not mounted, so no dotfiles, SSH keys or shell history - by design. The image carries git and the Docker CLI but not bazelisk, so inside the container the same operations go through docker compose -p evo-t1-prod -f "$STACK_HOST_PATH/docker-compose.yml".

  • --writable matters more than it looks. The official image sets HERMES_WRITE_SAFE_ROOT=/opt/data, so a file-tool write anywhere else is refused outright and no approval card even appears.

    To have the assistant edit files on the host, name the directory: --writable "${STACK_DEPLOY_PATH:-/opt/stack-deploy}" or the checkout path.

From a phone, or anywhere

The point of the assistant is that the operator leaves the desk and the box keeps working for them. Four doors reach the same agent, the same seeded config, the same skills and the same memory store; which one is open is a decision in .env, not a rebuild.

The API server door

The API server is the headless door: an iOS Shortcut or a Tasker profile can POST a prompt and read the answer with no browser and no dashboard login.

It ships off and the published mapping binds loopback, because this server "adds full access to the toolset, including terminal commands" per upstream, on a container that holds the docker socket.

Turning it on is two deliberate edits:

  1. the flag
  2. HERMES_API_BIND if something off this host should reach it

API_SERVER_KEY is generated by bootstrap with the other secrets and is required whenever the server is on; upstream fails closed rather than serving unauthenticated.

API_SERVER_MODEL_NAME (default hermes) is what a model-listing frontend shows.

API_SERVER_CORS_ORIGINS stays unset: a browser calls the dashboard, not this port, and an origin allowlist is only for a client you named on purpose.

The push door

Push is what makes a phone viable, because pull means opening a dashboard every time. It rides upstream's ntfy adapter and is configured in the assistant's own /opt/data/.env, not in compose:

Two reasons it lives on the volume:

  • the gateway registers the adapter from the presence of NTFY_TOPIC, so an empty NTFY_TOPIC= in compose would hand it a half-configured platform
  • a token in a container's environment is readable by anyone who can docker inspect it

Leave NTFY_ALLOWED_USERS unset and the channel is push-only - your phone gets the notices, and nobody can talk back to the agent through the topic. Set it (to the topic name) only for inbound, and only on a topic no one else can guess: upstream's own warning is that every publisher to a topic is treated as the same user.

NTFY_SERVER_URL defaults to https://ntfy.sh; a self-hosted ntfy keeps the notices on your hardware.

The questions you ask, and the verbs that answer them

What to ask from a phone is the same list you would run at the desk, and the coding-agents skill is what teaches the assistant to answer it:

  • what are my agents doing -> //scripts:coder-sessions -- list / show
  • what did it get stuck on -> tail <workspace> <session> 40, then quote the pane
  • tell it yes -> send <workspace> <session> "yes"
  • start one on repo X -> launch --dir /home/coder/<repo> <workspace>
  • wake me when it finishes -> watch <workspace> <session> 1800, then hermes send to the ntfy topic above
  • is the box healthy -> //scripts:hermes-shell -- check, and the host-diagnostics skill

Session control needs no credential and no open browser: the verbs read the Docker daemon by workspace label. See grok-build-and-agents.md.

Audit and drift

hermes-shell -- check answers "can I open the assistant". It cannot answer "is this still the assistant this repo describes", and the two come apart on a long-lived box: an operator edits the config inside the volume, a recreate reads a stale .env, a merge changes the seed and a seed-only-when-absent copy never takes it.

hermes-doctor answers the second question. It is read-only and prints key names with no value.

The commands

Where its facts come from

  • What it reads: the config the container actually loads, the environment it was created with, the mounts it was given, and the two seed files beside the checkout.

    The created environment is the fact and the .env beside the compose file is the intention: compose interpolated the former at create time, so a key can be right in the file and stale in the container until the next recreate.

    Every container-level fact comes from docker inspect or docker compose ps; nothing writes, restarts, recreates, or execs.

The check names, and the exit codes

  • The fifteen checks:

    • approvals (manual, with cron and unattended both deny)
    • terminal-cwd, write-root, web-lane, keyless-egress, mcp-servers, seed-drift, mount-identity, image-pin, model-key, dashboard, memories
    • anywhere-door (the API server's enabled/keyed/bound state and whether the push channel can be answered by strangers)
    • webapp-door (whether the v0.23.0 Webapp listener is switched on in the seed, in the volume copy, or in the container env; it is off, and the dashboard basic-auth triple does not cover that door)
    • agent-verbs (whether the assistant can still reach scripts/coder-sessions.sh and the socket those verbs read)

    The last two are the ones that keep the phone story honest: an open door nobody configured, and a closed door nobody can find, are the same class of surprise.

  • It reports, it does not gate. Exit 0 on a clean bill (warnings allowed), 1 when a check failed, 2 on a bad invocation, 5 when it cannot find a checkout. hermes-shell -- check stays the thing that decides whether to launch a session.

The findings it exists to catch

  • Three findings it exists to catch, each one measured on a live box:

    • terminal.cwd still carrying the ${STACK_HOST_PATH} token (Hermes

      Hermes

      The Nous Research host assistant, with the Web Dashboard and its approval prompts.

       validates that value with expanduser() alone, so the token reads as a missing directory while hermes config get prints it looking healthy)
    • STACK_HOST_PATH naming a directory with no checkout (compose mounts an empty directory over the repo and every container-level check still reads healthy)
    • a web block that stopped pinning searxng or flipped a keyless switch back on, which routes a search to a vendor's free tier while the config still looks local

  • --data DIR points the two volume checks at a directory instead of asking the daemon where the volume is mounted, so the audit can be run against a copy of one.

  • Run it before a --force re-seed and after a merge. The drift check names the file that differs and prints the hermes-bootstrap --data <mount> --force line that would overwrite it, which is the pair an operator wants side by side.

How the providers block declares aliases

  • The models come from a providers: block in hermes/config.yaml. Its litellm row declares the shared catalogue - the aliases that are not one of the Arc's own three weights - and each Arc row declares its weight with its default_model.

    Between them those declarations are every client-selectable alias in litellm/config.yaml, and a declaration is what makes an alias routable.

    Hermes

    Hermes

    The Nous Research host assistant, with the Web Dashboard and its approval prompts.

     matches a typed /model <alias> against the ids each row declares and routes it to the row that declares it, while a name no row declares is left on the current provider as an unknown hidden model.

    litellm/config.yaml owns the set, so an alias is added there and a row follows; the gate fails when the two drift apart, or when one alias ends up on two rows.

Route and model are separate switches

  • Route and model are two separate switches. A providers: row selects the route - base URL, api key, api mode - and the model for a turn is otherwise the value in the model: block.

    Measured on the shipped image, --provider <row> moves the route and takes that row's default_model with it:

    • --provider arc-chat sends "model":"chat"
    • --provider arc-coder sends "model":"coder"
    • --provider arc-coder-fast sends "model":"coder-fast"
    • --provider litellm sends "model":"agent" - that row's default_model is agent, which is also what the model: block holds

    -m/--model <alias> overrides it: --model agent-swarm sends "model":"agent-swarm", and --provider litellm --model chat sends "model":"chat".

    A run with no flags sends the model: block's value (agent) whatever rows exist, and hermes config set model.provider <row> changes the route and leaves that value alone - the default_model pickup is gated on the CLI flag, not on the config key.

The verbs that change the model

  • The verbs that do change the model:

    • /model <alias> inside a session
    • bazelisk run //scripts:hermes-shell -- -m <alias> from the host, which sets HERMES_MODEL in the container
    • hermes config set model.default <alias> to persist it in the live config under /opt/data

    model.model is the legacy spelling of that same value: the loader copies it to default only while the block carries none, and drops it after that - which is the shape a persisted /model writes.

    So after one in-session switch, hermes config set model.model <alias> prints a success line and changes nothing, and hermes config get model.model answers "Config key not set" for the same reason even when a model is set; read it back with hermes config get model.default.

The seed reaches the volume once

  • All of that lives in the seed, and the seed reaches the volume once: scripts/hermes-bootstrap.sh copies hermes/config.yaml into the data volume only when the file is absent.

    A box that ran an earlier seed therefore has no litellm row at all - --provider litellm names a row its config does not have, the eleven catalogue aliases are undeclared there, and with no row carrying discover_models: false the picker adopts compaction-fast off the proxy.

    Check it with bazelisk run //scripts:hermes-doctor -- diff, which names the file that differs and prints the hermes-bootstrap --data <mount> --force line that re-seeds it; a hand-edited volume copy is worth reading before you overwrite it.

  • Nous Portal is an optional upstream, not a default, and this page does not document it. Nothing here needs an account.

Web research

The assistant can look things up, and the query leaves through your own SearXNG

SearXNG

The keyless metasearch lane that answers the agent's web searches.

.

  • web_search goes to the stack's SearXNG

    SearXNG

    The keyless metasearch lane that answers the agent's web searches.

     container: the seeded config sets web.search_backend: searxng, and compose gives the container SEARXNG_URL=${STACK_HERMES_SEARCH_URL:-http://searxng:8181}.

    The variable's presence is what registers the provider (plugins/web/searxng reads SEARXNG_URL as its key env), and it is the only bundled web provider that needs no API key. The name resolves on the compose network, so this adds no published port.

  • Both keyless switches stay off, and that is the part that keeps the promise. agent/web_search_registry.py resolves a backend in five steps, and its last one is an anonymous free-tier ring - exa, parallel, firecrawl, keenable - reached with no key at all.

    A seed that named no backend and left web.keyless_fallback and web.keyless_rescue at their shipped true would answer a search from a vendor's public endpoint while looking local. With both false, a query either goes to your instance or fails on the box.

  • web_extract is deliberately unconfigured. SearXNG

    SearXNG

    The keyless metasearch lane that answers the agent's web searches.

     aggregates engine results and does not fetch pages, so the seed leaves web.backend and web.extract_backend empty and page extraction fails with "no extract provider configured".

    Set web.extract_backend yourself when you decide a fetch is worth a third-party extractor; nothing reaches one by default.

  • Query the lane the same way the agent does:

    • bazelisk run //scripts:search-check from a host shell counts results per engine, which is how an empty answer stays distinguishable from no answer
    • inside the container, curl -s -H 'Accept: application/json' "$SEARXNG_URL/search?q=hermes&format=json" is the exact request the provider makes

    The instance only answers JSON because searxng/settings.yml adds json to search.formats; without it the request is refused with 403 before the query is parsed.

  • Re-point the lane with STACK_HERMES_SEARCH_URL in .env (a sibling box, say) and recreate.

    An operator who wants a keyed provider sets web.search_backend plus that vendor's key env in the container themselves - the seed carries neither, and adding one is a decision with a privacy cost.

The skills directory

  • hermes/skills/ is tracked in git. Add a skill by editing the repo, never by editing the volume; the volume copy is not the record.

The deploy workspace

  • STACK_DEPLOY_PATH (default /opt/stack-deploy) is the deploy workspace: the one directory meant for clones, builds, and the compose project of a third-party project the assistant brings up.

    It is mounted at its own absolute path for the same reason STACK_HOST_PATH is - a bind source inside a project file the assistant writes has to resolve on the host daemon - and bootstrap fills it in without overwriting a path you set yourself.

    It is deliberately outside /home, so giving the assistant somewhere to work did not mean giving it your dotfiles. An existing container gains the mount on recreate, since restart keeps the old mounts.

Approvals

  • The seeded config sets approvals.mode: manual. cron_mode and unattended_mode are both deny, so a scheduled or unattended run cannot approve anything either.

  • Leave the mode on manual. off is --yolo: every mutating command executes on the host with no card.

  • terminal.backend: local keeps the dangerous-command checker active. The docker backend skips that checker, because it treats the container as the safety boundary - and here the container is mounted onto the host, so that boundary is not real.

  • Working agreement with the assistant: it explains the plan in chat, then waits for the approval card in the Chat tab before running anything mutating. If a run looks like it is acting without one, stop it and re-read the mode.

  • From the terminal door the same gate is inline in your tty: a dangerous command stops with [o]nce | [s]ession | [a]lways | [d]eny and does not proceed until you answer, with deny the default.

    An approval is scoped to the session you answer in, so a yes given over there does not cover a fresh session opened at this door. --yolo and HERMES_YOLO_MODE bypass the gate entirely; they have no place here.

Bootstrap and skills

What the first up seeds

The extra doors

  • The terminal door adds a way in for someone who already has a shell on this host, and opens no new listener, no new port and no new credential. hermes-shell authenticates nothing of its own: docker on that host is the credential, and it was always root-equivalent here.

    Its one guard is that the assistant's approvals stay manual on both doors.

  • The API server is the widest door here and ships closed. It carries the same toolset as the dashboard, terminal included, and its only gate is the bearer key, so it is off in compose and its host mapping binds loopback until an operator names both.

    Treat HERMES_API_SERVER_KEY as a root credential: rotate it by editing .env and recreating the container, and give a phone a Shortcut that holds it rather than a URL that carries it.

  • A push channel is an inbound door even when you only use it to listen. Every publisher to an ntfy topic is one identity to the gateway, so the push-only posture - NTFY_TOPIC and NTFY_PUBLISH_TOPIC set, NTFY_ALLOWED_USERS not - is the one this doc recommends, and the topic name is the secret.

  • The deploy workspace is writable by the assistant's file tools only when you say so with --writable, and the file tools refuse anything outside the image's HERMES_WRITE_SAFE_ROOT (the official default is /opt/data) with no prompt at all. Name the narrowest directory that finishes the job.
