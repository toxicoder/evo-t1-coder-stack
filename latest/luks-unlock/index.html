Unlock an encrypted host remotely

Configure the stack host so a reboot with an encrypted root can be answered from a laptop, and prove the boot image can do it before you reboot.

What's on this page

  • Why a reboot is the dangerous moment on an encrypted headless box
  • The one command that answers "can I unlock this from a laptop"
  • What install writes, and which file each line belongs to
  • The unlock itself, step by step, from the operator's own machine
  • What the check catches, and what it deliberately leaves alone

What this enables

  • Rebooting a server nobody is standing next to
  • Catching a config that looks right and boots dead, before the reboot
  • Reading the exact ssh command and host key fingerprint to expect

An Ubuntu server with a LUKS root stops in the initramfs on every reboot and waits for a passphrase. With no keyboard attached, that wait is the outage: the machine is up, the disks are unreadable, and the only fix is a person at the console. The distro answer is to move an SSH server and cryptsetup's unlock prompt into the initramfs, so the passphrase is typed over SSH from anywhere.

//scripts:luks-unlock writes that config and then proves the generated initramfs really contains the unlock path. The proof is the point: every one of the six settings involved fails by staying silent until the boot that needs it.

The command that matters

That is check, the default verb, and it writes nothing. It answers one question - if this box rebooted right now, could you decrypt it from a laptop - and closes with either ok: this box can be unlocked from a laptop after a reboot or error: do not reboot yet - N blocker(s).

Run it before every reboot of an encrypted box, and after any kernel or initramfs-tools update. It exits 1 when something blocks the unlock, so it fits in front of a maintenance script as a gate.

What install writes

install installs the two packages, writes the config, regenerates the initramfs, and then runs the same check over what it produced. Add --dry-run first and every write and command is printed as would: ... instead of executed. Nothing reboots.

FileLine it writesWhy it matters
/etc/cryptsetup-initramfs/conf-hookCRYPTSETUP=yWithout it the cryptroot scripts never enter the boot image, so there is nothing to type a passphrase into.
/etc/initramfs-tools/conf.d/zz-luks-unlockDROPBEAR=y, IP=, UMASK=0077, and HOOKS= when a list is in forceOne file this CLI owns, named to sort last so it wins over every other drop-in. IP= is what gives the boot image an address; UMASK=0077 keeps the packed key out of unprivileged hands.
/etc/dropbear/initramfs/authorized_keysthe operator's public key(s)Password logins are off in the initramfs. No key there means the SSH server refuses everyone, including you.
/etc/dropbear/initramfs/dropbear.confDROPBEAR_OPTIONS="-p 2222 -s -I 60 -j -k"-s keeps password logins off, -I bounds a session someone walked away from, and the port stays off the installed sshd's so the different host keys do not look like an attack. An existing DROPBEAR_OPTIONS is left alone.
/etc/dropbear/initramfs/dropbear_*_host_keygenerated with dropbearkey when none existdropbear refuses to start with no host key, and the package only creates them at install time.

The order is deliberate: the hook packs the authorized key at generation time, so a key written after update-initramfs is not in the image. That is why install ends by reading the image back.

The last one is worth dwelling on: check can read every config file and still be looking at an image GRUB cannot load, so an encrypted /boot is reported as a warning to verify by hand rather than cleared.

Static networks

A box with no DHCP gets the raw initramfs form, which is passed through untouched because initramfs-tools parses it, not this CLI:

--iface ens3 with --ip dhcp produces the same pinned-device shape with DHCP kept. A name the kernel never assigned is a blocker, not a typo you discover after the reboot: check compares it against /sys/class/net.

Two keys, two purposes

The unlock key authorizes a root shell on a machine whose disks are still sealed, and the initramfs image holding it sits on an unencrypted /boot. Anyone who can read /boot can read that public key, so treat it as a separate credential with its own purpose: a dedicated key whose private half lives on the laptop you bring to a reboot, not the key you push to every repository. UMASK=0077 keeps the image itself out of unprivileged hands, and the initramfs host keys stay separate from /etc/ssh on purpose - they are generated per boot image, and sharing them would leak which key the sealed machine answers to.

What this deliberately does not do

  • Reboot anything. The reboot is the operator's decision, made after a green check.
  • Edit /etc/crypttab or the LUKS headers. The volumes are read to decide whether the boot can open them. Key slots, passphrases and headers are never written, so this CLI cannot be the thing that destroys a key.
  • Enroll a TPM. systemd-cryptenroll is a different design with a different failure mode - a firmware update that changes the PCR policy seals the box with nobody in the loop - and it belongs in its own change.
  • Add an auto-reboot watchdog. A box sitting in the initramfs with dropbear listening is the recoverable state; rebooting on a timer destroys the recovery window and can turn one bad boot into a loop. -I bounds the session, and the listener stays.
