Navigating the repo with the Bazel graph

Answer what-depends-on-this with one bazelisk query instead of a grep sweep: the bazel-map CLI, the raw query predicates behind it, and the empty-result trap.

What this enables

  • Naming every suite that must move with a payload file in one query, in about 60 ms
  • Running the suites that cover the files you touched instead of the whole fast gate
  • Catching a payload directory no filegroup claims before the gates stay green by accident
  • Telling a rule class from a target name without opening a BUILD file
  • Stopping the late-gate discovery of a coupling rule the graph already recorded

This repo keeps its coupling in BUILD files: scripts/BUILD.bazel names the libs and payload groups each CLI reads, tests/BUILD.bazel names what each Bats

Why a query, not a grep

A sweep of this repo's own agent session logs measured the habits the graph is meant to replace. Corpus: the 199 parent sessions recorded for this checkout under ~/.grok/sessions/ before 2026-11-01, counted with jq and grep -c over each session's chat_history.jsonl. Every count is a floor, because a truncated tool result hides a call.

HabitMeasured
bazelisk query at all8 sessions, about 4%
rdeps() and somepath()never used in that corpus
Recursive grep for a structural questionthe default instrument: grep -rn outnumbered bazelisk query by an order of magnitude
//:test-fast re-run to learn one dependency48 sessions ran it; 16 ran it three or more times

The cost of not querying shows up late. In the sessions that hit a coupling rule, the first FAIL: // line appeared only after a hundred or more messages of editing: the rule was discoverable in the graph on message 1, and was instead discovered by running the gate. One agent audited //:stack_data by listing the repo's top-level directories rather than diffing the graph against git ls-files, which is the same question asked in a way that cannot answer it.

The verbs below are the shapes of those questions.

Flags, accepted anywhere in argv: --staged, --untracked, --ref <ref>, --all, --label-kind, --json, -h|--help. Exit codes: 0 when every named thing resolved, 1 on a query failure, 2 on a usage error (an unknown verb or flag, or a verb invoked without the argument it needs).

Use --json when you want to act on the answer. Prose (== section ==, ok:, note:, summary:) rides stderr and stdout carries only labels, one per line, which is the shape bazelisk test consumes:

Without --json the same labels are interleaved with the report lines, so piping them straight into another command feeds it ok: tests-for as an argument. Paths are repo-relative, and a batch costs one query: when a batch fails, the verb re-runs it per path and names the path the graph does not know instead of hiding every other answer.

Before a large edit: what moves with this file?

This is the question that costs the most sessions, because the answer is spread over four different mechanisms and each one is normally discovered by a failing gate.

The suites that read a payload

Seven suites, printed in about 60 ms. Change that file and those are the suites that go red; edit one of them and the same verb in the other direction tells you what it covers.

The twin template copies

templates/workspace/ and templates/devcontainer/ keep independent payload copies that must move together, and templates/common/ holds the files both consume as one shared copy. The verb matches basenames over the union of the three payload groups, so the twin set is the graph's answer rather than a convention you have to remember:

A per-tree file whose sibling tree has no counterpart is a warning: naming the group that claims it: that asymmetry is the drift worth knowing about before you edit, not after.

The filegroup that must claim a new payload file

A file the graph does not know is a warning naming that path, and the usual cause is a file you just created that no filegroup claims yet. owners answers "is this visible to the harness at all":

An empty list is the finding: no filegroup carries the file, so test-fast and lint never open it. The pair verb, unlisted, asks it per directory by diffing git ls-files against the graph's own source list. It skips Bazel

The map key a new scripts/*.sh needs, and the test a new function needs

A new scripts/*.sh is a Bazel

 target automatically (the package is generated from the directory), but it is not wired automatically: it needs a _SCRIPT_LIBS key (the scripts/lib closure it sources) and a _SCRIPT_PAYLOAD key (the payload groups it opens), both in scripts/BUILD.bazel. Until those keys land the graph does not know the file at all, which is worth saying out loud: rdeps reads the graph, not the filesystem.

That warning is the honest version of "nothing depends on this", and it is the reason to keep stderr with a query. Go to the gate that owns the map instead of guessing its label:

A script missing its key outright fails //scripts analysis before any test runs, and a script whose declared map disagrees with its sources is what that checker reports, naming the pairing and the direction. Once the keys are in place the same verb resolves the file, and tests-for scripts/bazel-map.sh lists //tests:bats_bazel_deps_test among its consumers. Every new function additionally owes one # @function block and one asserting test in exactly one suite, which test-with-bazel.md covers; //tests:shell_inventory and //tests:doc_coverage are the two gates, and both are test targets the graph can point you at before the gate does.

While you iterate: which tests, and when you still owe a full pass

scope derives the test list from what this checkout changes, which is the loop that replaces re-running the whole fast gate after every edit:

Default scope reads git diff HEAD; add --staged for the index, --untracked to count files git does not track yet (a file you just created is exactly the case worth covering), or --ref <ref> for what this branch adds over a base. --all also lists the aggregate suites that reach everything (//:test, //:test-fast, //:test-all and //tests:bats), which is useful when you want the full set named explicitly rather than the leaf suites you can invoke. The default already includes the lint targets: every test rule here, //lints:shell and //lints:shfmt among them, is an sh_test.

Two things scope tells you that a habit of bazelisk test //:test-fast hides:

  • An empty result means run everything. Nothing changed against HEAD, or the change touches no file the graph tracks, and scope says so and points at //:test-fast.

The uncached pass is not replaced. bazelisk test replays a cached PASS for an action whose inputs did not change, so the derived list proves your change against whatever actually rebuilds, and one bazelisk test //:test-fast --nocache_test_results remains the pass you owe before the PR, per building-with-bazel.md. Use the derived list for the loop and keep the full uncached pass for the end, instead of paying for sixty suites to learn one thing per edit.

What a target reads, and why an unlisted directory is invisible

//:test-fast runs in a sandbox: an action sees its declared inputs and its runfiles tree, not the checkout. So "what does this target read" is a real question with a printed answer, and the answer has two depths worth keeping separate.

The direct inputs are the data the dependency maps write, which is what you edit when a target needs one more payload group:

The files it can actually open are the transitive closure of those groups, which is what the verb prints:

That target resolves to 198 source files through 25 declarations: the gap is the filegroup and scripts/lib expansion under each label. labels("data", ...) is the narrower question ("what does the BUILD file say"), files is the wider one ("what is in the sandbox"), and the two disagreeing is usually the bug.

This is why an unlisted payload directory stays invisible rather than being checked loosely: a file that travels in no runfiles tree is a file no sandboxed action can open, so test-fast and lint never read it and never fail. Nothing prints a warning about that. owners <path> and unlisted <dir> are the two ways to ask, and they are the difference between a payload the harness guards and a payload nobody has ever executed.

Raw query recipes when a verb does not fit

Every verb is one of these, so a question outside the verb set needs one predicate, not a grep plan. All of these run warm in about 50 to 70 ms.

PredicateQuestion it answers
rdeps(//..., "path")what depends on this file
deps(//target)what this target depends on, transitively
kind("sh_test", ...)narrow to the rules you can act on
attr("name", "re", pkg:*)find a target by a name fragment
labels("data", //target)the groups a target declares as its inputs
somepath(a, b)is there any path from this suite to that file
A intersect B, A except Bcombine two result sets
